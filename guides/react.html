React.js Interview Guide

Hooks, reconciliation, memoization, and the architecture decisions behind data-heavy dashboards — framed around real banking-UI work (AG Grid, trade lifecycle data, MTM reporting).

1. Technology overview

React is a declarative UI library built around a component tree and a reconciliation algorithm ("the diffing algorithm") that decides the minimum set of DOM mutations needed when state changes. Modern React is almost entirely function components + hooks. At the senior/lead level, interviewers care less about "what does useState do" and more about: do you understand why re-renders happen, can you architect a large data-heavy app (your AG Grid / trade-data background is exactly this), and can you make correct trade-offs under performance pressure.

2. Basic questions

Basic What is the Virtual DOM and why does React use it?
What

The Virtual DOM is a lightweight in-memory tree of plain JS objects that mirrors the real DOM. On state change, React builds a new virtual tree, diffs it against the previous one (reconciliation), and computes the minimal set of real-DOM operations needed — then applies them in one batch.

Why

Direct DOM manipulation is expensive (layout/reflow); batching minimal updates through a JS-object diff is far cheaper than naively re-rendering the whole page, especially for a grid rendering thousands of trade rows.

Common mistake

Saying "Virtual DOM makes React faster than vanilla JS" unconditionally — a hand-tuned vanilla-JS update can beat React; the VDOM's real win is developer ergonomics (write declarative code, get reasonable performance for free) not raw speed.

Basic Controlled vs uncontrolled components?

Controlled: the form element's value is driven by React state (value + onChange) — single source of truth, easy validation, but a re-render per keystroke. Uncontrolled: the DOM holds its own state, read via a ref when needed — less re-rendering, useful for simple forms or integrating non-React widgets (e.g. wrapping a third-party grid input).

Basic What problem do keys solve in lists?

Keys give React a stable identity for each list item across renders so it can match old and new elements correctly instead of diffing by index. Using array index as a key breaks when items are reordered/inserted/deleted — React will misattribute state (e.g. a text input's focus/value jumps to the wrong row) because it thinks "item at index 2" is the same element even though the underlying data moved.

Basic What is JSX, and how does it actually get compiled?

JSX is syntax sugar with no native browser support — Babel (or the compiler built into your bundler) transforms it into plain function calls before it ever reaches the browser. Historically this meant React.createElement(type, props, ...children) calls; the newer JSX transform (default since React 17) compiles to calls against a dedicated react/jsx-runtime import instead, which no longer requires React to be in scope in every file just to use JSX. Either way, JSX itself produces plain JS objects describing the element tree — it's the Virtual DOM's actual data shape, not markup.

Basic Do you still need to know class components, and how do their lifecycle methods map to hooks?

Functional components + hooks are the standard for all new code, but class components still turn up in legacy codebases, and — importantly — error boundaries still require a class, since componentDidCatch/static getDerivedStateFromError have no hook equivalent. PureComponent is the class-component equivalent of React.memo: both perform a shallow comparison of props (and, for PureComponent, state) to skip unnecessary re-renders. 

useEffect(() => {
  console.log('mounted');                // ~ componentDidMount
  return () => console.log('unmounted'); // ~ componentWillUnmount
}, []);

useEffect(() => {
  console.log('data changed');           // ~ componentDidUpdate, scoped to `data`
}, [data]);

This isn't a strict 1:1 mapping conceptually — a single useEffect with cleanup models "synchronize with this dependency," which subsumes mount/update/unmount rather than mirroring them as three separate lifecycle events. Dan Abramov's framing is worth stating explicitly if asked: effects synchronize, they don't run on lifecycle events.

3. Intermediate questions

Intermediate What are the Rules of Hooks, and why do they exist mechanically (not just "because the docs say so")?

Two rules: only call hooks at the top level (never inside conditionals, loops, or nested functions), and only call them from React function components or other custom hooks. The mechanical reason: React doesn't track hook state by name — it tracks it by call order, associating each useState/useEffect call with a slot in an internal linked list attached to that component's fiber. If a hook call is skipped conditionally on one render but not another, every subsequent hook's position shifts by one, and React silently reads/writes the wrong slot — corrupting state without necessarily throwing an error immediately. This is also why the ESLint react-hooks/rules-of-hooks plugin is treated as close to non-negotiable on a real team: the failure mode is subtle state corruption, not a clean crash.

Intermediate Explain the dependency array in useEffect — and the stale closure trap.
What

The dependency array tells React when to re-run the effect. Omit it → runs after every render. Empty array → runs once on mount. With values → re-runs when any listed value changes (by Object.is comparison).

The trap
function Timer() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1); // always uses count from the render that registered this effect
    }, 1000);
    return () => clearInterval(id);
  }, []); // stale closure — count is frozen at 0 forever
}

Fix: use the functional updater setCount(c => c + 1), which doesn't depend on the captured count at all, or add count to the dependency array (recreating the interval each tick).

Follow-up

"When would you intentionally suppress the exhaustive-deps lint rule?" — rarely, and only with a written comment explaining why (e.g. an effect that should only run once but reads a ref/prop that's stable in practice).

Intermediate useMemo vs useCallback vs React.memo — when does each actually help?
Tool Memoizes Use when
useMemo A computed value Expensive calculation (sorting/filtering thousands of grid rows)
useCallback A function reference Passing a callback to a memoized child, or as an effect dependency
React.memo A component's render output Child re-renders often with the same props

Common mistake: memoizing everything by default — each memo has its own comparison cost, so wrapping cheap components/values in useMemo/React.memo can make things slower. Profile first (React DevTools Profiler), then memoize the actual bottleneck — for you, that's typically grid row renderers and derived/sorted datasets, not every small presentational component.

Intermediate Custom hooks vs Higher-Order Components (HOCs) — when to reach for which?

Both share cross-cutting logic (data fetching, subscriptions, permissions checks). HOCs wrap a component and inject props — they predate hooks and cause "wrapper hell" (deeply nested component trees, prop name collisions, harder debugging in DevTools). Custom hooks share stateful logic without adding to the component tree at all — you call useAuth() inside the component and get exactly the values you need. In new code, prefer custom hooks; HOCs still show up in older codebases and libraries (e.g. some HOC-based patterns in class-based legacy code), so you should be able to read and migrate them.

Intermediate Context API vs Redux — how do you decide?

Context is built-in dependency injection for values that rarely change (theme, current user, locale) — every consumer re-renders whenever the Context value changes, with no built-in selector/memoization, which makes it a poor fit for high-frequency state. Redux (or RTK/Zustand) adds a predictable store, middleware (thunks/sagas for side effects), time-travel debugging, and — critically — selector-based subscriptions so components only re-render when the specific slice they read changes. For a trading/reconciliation dashboard with frequently updating tables, Redux-style selector subscriptions usually outperform raw Context. This same reasoning applies to prop drilling more broadly — the three usual fixes, in order of how often they're reached for: Context (broadly-needed, infrequently-changing data), a state library (complex cross-cutting state), or plain component composition (passing components as children/props instead of threading data through layers that don't use it) — composition is the simplest fix and is frequently overlooked.

Intermediate useEffect vs useLayoutEffect — when does the difference actually matter?

useEffect runs after the browser has painted — asynchronously, so it never blocks the visual update. useLayoutEffect runs synchronously, before the browser paints, blocking the visual update until it finishes. Reach for useLayoutEffect specifically when you need to measure the DOM (e.g. getBoundingClientRect()) and synchronously adjust something based on that measurement before the user sees anything — a tooltip repositioning itself based on its own rendered size, for example. Using useEffect for that same case causes a visible one-frame flicker: the tooltip briefly renders in the wrong position, then jumps. For anything that doesn't need to block paint (data fetching, subscriptions, logging), useEffect is the correct default — useLayoutEffect used unnecessarily costs real performance since it blocks the browser from painting at all until it completes.

Intermediate What is useRef actually for, beyond DOM access?

useRef returns a mutable { current: ... } box that persists across renders without triggering a re-render when it changes — this is its defining property, distinct from state. It's used for two different things: (1) direct DOM node access (inputRef.current.focus()), and (2) holding any mutable value you deliberately don't want tied to the render cycle — a debounce timer ID, a previous-value snapshot for comparison, a flag tracking whether a component is still mounted inside an async callback. Reaching for a ref instead of state for something that should actually trigger a re-render (e.g. a value shown in the UI) is a common mistake — if the UI needs to reflect the value, it has to be state; refs are for values the render output doesn't depend on.

4. Advanced questions

Advanced Explain reconciliation and the diffing heuristics React actually uses.

React's diff is O(n) instead of the theoretical O(n³) for general tree diffing, because it makes two simplifying assumptions: (1) elements of different types at the same position produce entirely different trees — React tears down the old subtree and builds a new one rather than diffing children; (2) elements of the same type are compared prop-by-prop and children are diffed using the key-based list algorithm. This is why swapping a <div> for a <section> at the same position remounts everything below it (losing state), while keeping the same tag and changing props is cheap.

Advanced What is Fiber, and how do concurrent features (useTransition, useDeferredValue) actually improve perceived performance?

Fiber (since React 16) reworked reconciliation into an incremental, interruptible process — each Fiber node represents one unit of work, and React can pause, abort, or resume work instead of walking the whole tree synchronously in one uninterruptible pass. This is the foundation concurrent rendering builds on: React can start rendering an update, and if something more urgent arrives (the user typing), pause the in-progress low-priority render and handle the urgent one first.

useTransition lets you mark a state update as non-urgent ("this can render whenever, don't block typing") — React keeps showing the old UI (optionally with an isPending flag you can render a subtle loading indicator from) while the transition renders in the background, then swaps in the new UI once ready. useDeferredValue does the same thing but for a value rather than a state setter — useful when you don't own the state update itself (e.g. a value passed down as a prop) but still want to defer the expensive re-render it triggers. Both solve the same real problem: a large, expensive re-render (filtering 50,000 grid rows on every keystroke) blocking the input from feeling responsive.

Advanced How did React 18 change automatic batching, and why does that matter for code that worked fine in React 17?

Batching means React groups multiple state updates from the same event into a single re-render instead of re-rendering after each individual setState call. Before React 18, this only happened automatically inside React's own event handlers — state updates inside a setTimeout, a native (non-React) event listener, or a resolved Promise each triggered a separate synchronous re-render. React 18's automatic batching extends this to all updates by default, regardless of where they originate. 

// React 17: two re-renders (setTimeout is outside React's batching)
// React 18: one re-render (batched automatically)
setTimeout(() => {
  setCount(c => c + 1);
  setFlag(f => !f);
}, 1000);

This is mostly a transparent performance win, but it can surface a latent bug: code that relied on reading a state value between two setState calls (assuming a synchronous re-render happened in between) now sees stale values, since both updates are batched into a single render pass. If you genuinely need to force a synchronous, unbatched update, flushSync from react-dom opts a specific update out of batching — rarely needed, but worth knowing exists.

Advanced How would you virtualize a table with 50,000 rows (relevant to your AG Grid experience)?
Approach

Never render all 50,000 DOM rows. Render only the rows visible in the viewport (plus a small overscan buffer), absolutely position them using a calculated transform: translateY(), and keep a single tall "spacer" element so the scrollbar reflects the full logical height. On scroll, recompute which row indices are visible and swap the rendered slice — this is exactly what AG Grid, react-window, and react-virtualized do internally.

Trade-offs

Virtualization adds complexity (variable row heights are harder; browser find-in-page and screen readers see fewer DOM nodes than logical rows, hurting naive accessibility unless you add ARIA live-region/announcement handling). For financial data grids with column pinning, grouping, and cell editing, a mature library (AG Grid) is usually the right call over hand-rolling it — which maps directly to your production choice at US Bank.

Advanced Error boundaries — what do they catch, and critically, what do they NOT catch?

Error boundaries (class components implementing componentDidCatch/getDerivedStateFromError — no hook equivalent exists yet) catch render-phase errors, lifecycle errors, and errors in constructors of the tree below them. They do not catch: errors in event handlers (use plain try/catch there), errors in async code (setTimeout/promises), server-side rendering errors, or errors thrown in the boundary itself. This gap is a common "gotcha" question — many candidates assume boundaries catch everything.

Advanced Walk through debugging an infinite re-render loop caused by a useEffect with an object literal dependency. 
function Widget({ userId }) {
  const [data, setData] = useState(null);
  const options = { userId, includeArchived: false }; // NEW object every render

  useEffect(() => {
    fetchData(options).then(setData);
  }, [options]); // "changes" every render — infinite loop
}

Object/array/function literals are compared by reference, not value — { userId, includeArchived: false } creates a brand-new object on every render, so Object.is (what the dependency array uses) always reports it as "changed," re-running the effect, which triggers a state update, which triggers another render, which creates another new object — the loop. React DevTools' Profiler or a simple console.log inside the effect showing it firing every render is usually how this gets spotted in practice. Fix: either move the object construction inside the effect itself (so it's not a dependency at all), destructure to only the primitive values actually needed ([userId] instead of [options]), or wrap it in useMemo if it genuinely needs to be a stable reference elsewhere too.

Advanced How can React.memo combined with useCallback still fail to prevent re-renders? 
function Parent() {
  const [count, setCount] = useState(0);
  const handleClick = useCallback(() => console.log('clicked'), []);

  return (
    <MemoChild
      onClick={handleClick}
      config={{ theme: 'dark' }} // NEW object every render — breaks memo anyway
    />
  );
}
const MemoChild = React.memo(function Child({ onClick, config }) { /* ... */ });

React.memo does a shallow comparison of all props — memoizing the function with useCallback only stabilizes that one prop. Any other prop that's a fresh object/array/inline-function literal each render (like config here) still fails the shallow-equality check and forces MemoChild to re-render anyway, silently defeating the whole optimization. The fix is the same principle as the infinite-loop question above: every reference-type prop passed to a memoized component needs its own stable identity (via useMemo for objects/arrays, useCallback for functions) — memoizing only some of them doesn't help.

5. Expert-level & scenario-based

Expert Scenario: users report a form losing typed input intermittently. Diagnose.

Three usual suspects, roughly in order of likelihood: (1) the component is remounting rather than re-rendering — a changing key prop, or a parent conditionally rendering the form via a ternary that swaps between different component types, forces React to tear down and rebuild the whole subtree (per the reconciliation rules above), wiping local state entirely; (2) a controlled input's value is being overwritten by a race condition — an async/debounced source (a save-draft API call, a WebSocket update) resolves after the user has already typed further and stomps the field's value with stale data; (3) for an uncontrolled input specifically, a parent re-render resetting the defaultValue prop does nothing after mount (uncontrolled inputs only read defaultValue once), so that's rarely the actual cause — but a parent conditionally re-mounting the uncontrolled input itself would reset it. Isolate which of the three by checking: does the DOM node identity change (React DevTools "highlight updates"), is there an async write racing the user's typing, or is a key/conditional render swapping component types.

Expert Scenario: design the state management for a dashboard combining a user session, feature flags, several independently-loading server-fetched widgets, and a multi-step wizard's local form state.

The right answer isn't "put it all in Redux" — it's scoping each piece of state to the tool actually suited to it: session and feature flags rarely change and are needed broadly → Context. Widget data is server state with its own per-widget loading/error/refetch needs → React Query or RTK Query, which already solves caching and invalidation rather than reinventing it in a manually-managed Redux slice. The wizard's form state is local, short-lived, and irrelevant outside that one flow → a useReducer scoped to the wizard component itself, not the global store. Good state-management design is fundamentally about scoping state to where it's actually needed rather than defaulting everything into one global store "to be safe" — the interviewer is listening for exactly this framing, not a specific library choice.

Expert Scenario: your reconciliation dashboard re-renders the entire trade table on every WebSocket price tick, causing visible jank. How do you fix it at an architectural level?

1) Isolate high-frequency state: move the price/tick state out of the parent and into the individual row component (or a dedicated store slice with per-row selectors) so only the affected row re-renders, not the whole table. 2) Batch ticks — if updates arrive faster than the browser can paint, throttle/coalesce them to animation-frame boundaries with requestAnimationFrame. 3) Use windowing/virtualization so off-screen rows never re-render regardless. 4) Confirm with the Profiler which component is actually the bottleneck before optimizing — this is the same production trade-off you'd have hit reconciling FX/MTM data in real time.

Expert Output-based: what's wrong with this code, and what will the user actually see? 
function Search({ query }) {
  const [results, setResults] = useState([]);
  useEffect(() => {
    fetchResults(query).then(setResults);
  }, [query]);
  return <List items={results} />;
}

If the user types quickly, multiple fetches fire and there's no guarantee they resolve in the order they were sent — a slow response for an earlier keystroke can overwrite a fresher result (the same race condition covered in the JS guide). Fix with a cleanup flag/AbortController inside the effect, or delegate to a data-fetching library (React Query/SWR) that handles request cancellation and de-duplication out of the box.

6. Architecture & design questions

  • "Design the component structure for a trade blotter with filtering, sorting, inline editing, and row-level permissions." — talk through: container/presentational split, where filter/sort state lives (URL params vs local state vs store), memoized selectors for derived/filtered data, virtualization, and how permission checks gate editable cells without duplicating logic per column.
  • "How do you structure a large React app for a team of 10+ engineers?" — feature-folder structure over type-folder structure, a shared design-system/component library, strict boundaries via lint rules (no cross-feature imports), and a documented state-management convention (what goes in Redux vs local state vs server-cache library).
  • "How would you migrate a large class-component codebase to hooks incrementally, without a big-bang rewrite?" — convert leaf/simple components first; keep lifecycle-heavy, complex components as classes until the custom-hook replacement is proven on simpler cases; add solid test coverage before migrating each component so a regression is caught immediately; use a codemod for repetitive, mechanical patterns; and avoid mixing class and hook patterns within a single component's own logic, since that makes review diffs much harder to reason about even if the app as a whole is mid-migration.

7. Coding challenges

Problem: implement useDebounce(value, delay) — a debounced version of a fast-changing value, without debouncing the keystroke handler itself 
function useDebounce(value, delay = 300) {
  const [debouncedValue, setDebouncedValue] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => setDebouncedValue(value), delay);
    return () => clearTimeout(timer); // cancels the pending update if value changes again first
  }, [value, delay]);

  return debouncedValue;
}

// Usage — the input itself stays instantly responsive; only the search fires debounced
function Search() {
  const [query, setQuery] = useState('');
  const debouncedQuery = useDebounce(query, 300);

  useEffect(() => {
    if (!debouncedQuery) return;
    fetchResults(debouncedQuery);
  }, [debouncedQuery]);

  return <input value={query} onChange={e => setQuery(e.target.value)} />;
}

Explanation: every keystroke updates query immediately, keeping the input controlled and responsive — but the effect's cleanup function cancels the pending timeout each time value changes again before delay elapses. That cancel-and-reschedule cycle is the debounce mechanism, expressed declaratively via effect cleanup instead of a manually managed timer ref. Common mistakes: debouncing the onChange handler directly instead of the derived value (makes the input itself feel laggy); forgetting the cleanup function (multiple stale updates fire); missing delay in the dependency array if it can change at runtime. Follow-up: "How would you support an immediate/leading-edge option?" — fire once immediately on the first call, then apply the normal trailing-edge debounce to subsequent calls within the window (same pattern as the JavaScript guide's throttle follow-up).

Problem: build a reusable useFetch(url) hook that cancels stale requests 
function useFetch(url) {
  const [state, setState] = useState({ data: null, error: null, loading: true });

  useEffect(() => {
    const controller = new AbortController();
    setState({ data: null, error: null, loading: true });

    fetch(url, { signal: controller.signal })
      .then(res => {
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        return res.json();
      })
      .then(data => setState({ data, error: null, loading: false }))
      .catch(error => {
        if (error.name !== 'AbortError') {
          setState({ data: null, error, loading: false });
        }
      });

    return () => controller.abort();
  }, [url]);

  return state;
}

Explanation: AbortController cancels the in-flight request on unmount or whenever url changes again before the previous request resolves — this is what prevents both the classic "setState on an unmounted component" warning and the race condition where a slow, stale response overwrites a newer one (the same class of bug covered in the JavaScript and Redux guides' race-condition questions). The AbortError case is deliberately excluded from the error state, since a cancellation isn't a real failure the UI should surface. Common mistakes: not aborting on cleanup at all (race conditions, memory leaks); setting the loading state outside the effect (captures a stale closure); not distinguishing an intentional abort from a genuine network error. Follow-up: "How would you add caching so repeated calls to the same URL don't refetch?" — this is essentially the exact problem React Query/RTK Query already solve; a good answer names that as the point where you'd reach for a library instead of continuing to hand-roll it.

9. Common mistakes & debugging

Frequent production bugs Mutating state directly (state.push(x) instead of returning a new array) — React won't detect the change; missing cleanup functions in useEffect causing "can't update state on an unmounted component" warnings; using array index as key on reorderable lists; overusing Context for frequently-changing values and causing app-wide re-renders; overusing useEffect to compute derived values that could just be calculated directly during render; storing server data in local component state instead of a proper cache layer (React Query/RTK Query), causing duplication and staleness bugs.

10. Frequently asked at top product companies

  • Meta/Google style: "Implement useDebounce as a custom hook" or "Build a typeahead/autocomplete component from scratch."
  • Amazon style: System-design-flavored — "design an infinite-scroll product list" (ties directly into your virtualization/AG Grid depth above).
  • Airbnb/Uber style: "Build a controlled multi-step form with validation and back/forward state preservation."

Machine-coding rounds also draw from a fairly consistent pool of "build this from scratch" prompts: a Kanban board with draggable cards, a lazy-loading file-explorer tree, tic-tac-toe/minesweeper (logic/UI separation is what's actually graded), a JSON-schema-driven form generator, or a rate-limited cancellable typeahead with results caching. What separates a senior/lead answer isn't finishing fastest — it's clear separation of concerns (presentational vs. container, logic extracted into custom hooks), naming edge cases out loud before being asked (empty/loading/error/race conditions), and stating trade-offs explicitly ("I'm using array state here for simplicity; in production I'd normalize this by id").
