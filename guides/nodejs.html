Node.js & Express Interview Guide

The event loop under the hood, middleware pipelines, streams, and the backend-adjacent knowledge that separates a frontend engineer from a "full-stack-capable" senior candidate.

1. Technology overview

Node.js runs JavaScript outside the browser on the V8 engine plus libuv, a C library that provides the event loop and non-blocking I/O. Express is the thin, unopinionated web framework layered on top — routing, middleware chain, request/response helpers. Given your resume shows working knowledge of Node.js/Express (REST API integration, CI/CD, some backend exposure alongside a primarily frontend role), interviewers typically probe just deep enough to confirm you can reason about async I/O correctly and aren't just pattern-matching Express boilerplate.

2. Basic questions

Basic Why is Node.js described as "single-threaded" when it can clearly handle many concurrent requests?

JavaScript execution itself runs on one thread (the event loop), but I/O operations (file system, network, DNS) are delegated to the OS or to libuv's thread pool, and their callbacks are queued back onto the single JS thread when they complete. So Node handles concurrency by never blocking that one thread on I/O — it's concurrent (many operations in flight) but not parallel (only one line of JS executes at a time) unless you explicitly use worker threads or child processes for CPU-bound work.

Basic What's the difference between module.exports (CommonJS) and ES Modules export?

CommonJS (require/module.exports) loads synchronously and resolves modules at runtime — Node's original module system. ES Modules (import/export) are statically analyzable (imports are resolved before execution), support tree-shaking, and are the standard used across the frontend tooling ecosystem. Node supports both today, but mixing them in the same project without proper configuration ("type": "module", file extensions) is a common source of build errors.

Basic What does Express middleware actually do, and what's the significance of calling next()? 
app.use((req, res, next) => {
  console.log(req.method, req.url);
  next(); // hands off to the next middleware/route handler
});

Middleware functions run in the order they're registered, each receiving (req, res, next). Calling next() passes control to the next function in the chain; not calling it (without sending a response) leaves the request hanging forever — a very common beginner bug. Middleware can short-circuit the chain entirely by sending a response instead of calling next() (e.g. an auth-check middleware returning 401 and never calling next()).

3. Intermediate questions

Intermediate Walk through the event loop's phases — what actually happens after server.listen() and a request comes in?

The event loop cycles through phases each tick: timers (due setTimeout/setInterval callbacks) → pending callbacks (deferred I/O callbacks from the previous cycle) → poll (retrieve new I/O events, execute their callbacks — this is where most request handling happens) → check (setImmediate callbacks) → close callbacks. Between every phase transition, Node drains the microtask queue (Promise callbacks, process.nextTick — which actually runs even before other microtasks). For a typical Express request: the poll phase picks up the incoming connection's data event, your route handler runs (synchronously, or scheduling further async work like a DB query), and the response is written back once that resolves.

Intermediate How do you handle errors in async Express route handlers correctly? 
// Express 4 does NOT catch rejected promises automatically
app.get('/trades/:id', async (req, res, next) => {
  try {
    const trade = await tradeService.findById(req.params.id);
    res.json(trade);
  } catch (err) {
    next(err); // hands off to the error-handling middleware
  }
});

// Centralized error handler — must have 4 args for Express to recognize it
app.use((err, req, res, next) => {
  console.error(err);
  res.status(err.statusCode || 500).json({ message: err.message });
});

Common mistake: throwing inside an async handler without a try/catch and without next(err) — in Express 4, an unhandled rejection in a route handler doesn't automatically reach the error middleware and can crash the process or hang the request (Express 5 fixes this by catching rejected promises automatically, but many production codebases are still on Express 4).

Intermediate Streams — why would you use one instead of reading a whole file/response into memory?

A stream processes data in chunks as it arrives instead of buffering the entire payload in memory first — critical for large files or responses (exports, CSV downloads, large trade-history reports) where loading everything into memory would spike RAM usage and delay the first byte sent to the client. fs.createReadStream(file).pipe(res) starts sending data to the client as soon as the first chunk is read, rather than waiting for the whole file to load.

4. Advanced questions

Advanced Your Node service does CPU-intensive work (e.g. generating a large PDF/report) and it's blocking other requests. How do you fix it?

Because JS runs on one thread, a synchronous CPU-bound operation blocks the entire event loop — no other request can be processed until it finishes, even ones that don't touch the same data. Fixes: (1) offload the work to a worker_thread (true parallel execution on a separate thread, communicating via message passing) so the main thread stays free to handle other requests; (2) move the work to a separate background job/queue (e.g. a job processed by a worker service) and return a "processing" response immediately, notifying the client when done; (3) for the cluster level, run multiple Node processes (via the cluster module or a process manager like PM2) behind a load balancer so one busy process doesn't block all traffic — though this doesn't fix a single blocked request, it limits the blast radius.

Advanced JWT vs session-based authentication — trade-offs for a banking-style app?
Session-based JWT
State Server-side (session store: Redis/DB) Stateless — all claims in the token
Revocation Instant (delete server-side session) Hard — token valid until expiry unless you maintain a blocklist (which reintroduces server state)
Scaling Needs a shared session store across instances Naturally stateless across instances
Payload exposure Opaque session ID only Decodable (not encrypted) — never put secrets in the payload

For a financial application where instant session revocation (a compromised device, an offboarded employee) genuinely matters, session-based auth or short-lived JWTs with a refresh-token rotation strategy (and a server-side revocation list for refresh tokens) is usually preferred over long-lived stateless JWTs.

5. Expert-level & scenario-based

Expert Scenario: a Node API's memory usage climbs steadily over days until it's restarted. How do you diagnose a memory leak in production?

Take heap snapshots at intervals (via --inspect and Chrome DevTools, or heapdump) and diff them to see which object types keep growing. Common culprits in Express apps: an in-memory cache/Map with no eviction policy accumulating entries forever; event listeners added per-request but never removed; a module-level array/array-like structure (e.g. a request log) that's appended to but never trimmed; closures in long-lived middleware capturing large per-request objects. Add process-level monitoring (memory/CPU metrics scraped over time) so a leak shows up as a trend before it causes an outage, not just as a post-mortem investigation.

Expert Output-based: what will this log, and why does the order matter here? 
console.log('start');
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
process.nextTick(() => console.log('nextTick'));
Promise.resolve().then(() => console.log('promise'));
console.log('end');
// start, end, nextTick, promise, timeout OR immediate (order between these two is not guaranteed outside I/O cycles)

process.nextTick callbacks run before the Promise microtask queue, and both run before the event loop moves to any phase (timers or check). setTimeout(fn, 0) vs setImmediate ordering is actually non-deterministic when called from the main module (it depends on process performance/timing), but becomes deterministic (immediate always first) when both are scheduled from inside an I/O callback, because setImmediate runs in the check phase immediately after the poll phase where I/O callbacks fire.

6. Common mistakes & debugging

Frequent review comments Using synchronous fs/crypto methods (fs.readFileSync, bcrypt.hashSync) on the request path, blocking the event loop for every concurrent request; not validating/sanitizing request bodies, opening SQL/NoSQL injection or prototype-pollution risks; storing secrets in JWT payloads (they're base64-decodable, not encrypted); missing centralized error-handling middleware, leaking stack traces to clients in production; not setting appropriate CORS and security headers (helmet).

7. Frequently asked at top product companies

  • Amazon/general backend-adjacent style: "Explain the event loop phases and where process.nextTick fits" — near-universal question.
  • Fintech-style (relevant to your background): "How would you design authentication/session handling for a banking dashboard with strict revocation requirements?"
  • Systems-leaning companies: "How do you scale a Node service horizontally, and what state has to move out of process memory to make that safe?" (sessions, in-memory caches, rate-limit counters → move to Redis/shared store).
