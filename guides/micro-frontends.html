Micro Frontends Interview Guide (Deep Dive)

Beyond "when to use them" (covered in System Design) — the actual mechanics: Module Federation, shared dependencies, cross-MFE routing, styling isolation, and independent deployment.

1. Overview

The System Design guide covers when micro-frontends make organizational sense. This guide goes one layer deeper into how they actually work — the specific technical mechanisms (Module Federation being the dominant modern approach) that let independently-built, independently-deployed frontend applications compose into one cohesive product at runtime.

2. Basic questions

Basic What is Webpack Module Federation, at a mechanical level? 
// Remote app's webpack config — exposes a module
new ModuleFederationPlugin({
  name: 'tradesApp',
  exposes: { './TradeGrid': './src/TradeGrid' },
  shared: ['react', 'react-dom'],
});

// Host app's webpack config — consumes it
new ModuleFederationPlugin({
  remotes: { tradesApp: 'tradesApp@https://trades.example.com/remoteEntry.js' },
});

// Host app code — dynamic import, resolved at RUNTIME, not build time
const TradeGrid = React.lazy(() => import('tradesApp/TradeGrid'));

Module Federation lets one independently-built and independently-deployed application (the "remote") expose specific modules that another application (the "host") can import and render at runtime, without either being compiled together at build time. This is the key architectural shift from older micro-frontend approaches (iframes, or build-time npm package composition): the actual code is fetched and integrated live, in the browser, from wherever each piece was independently deployed.

3. Intermediate questions

Intermediate How does Module Federation avoid every micro-frontend shipping its own separate copy of React?

The shared config option declares dependencies that should be shared across host and remotes rather than duplicated. At runtime, Module Federation negotiates versions: if the host and a remote both need React and their version ranges are compatible, only one copy is actually loaded and both use it; if versions are genuinely incompatible, each falls back to loading its own copy (at the cost of duplicated bytes, but without breaking). This negotiation is what keeps a multi-team micro-frontend product from shipping five copies of React to every user by default — but it does require teams to actively coordinate on shared-dependency version ranges, which is itself an ongoing cross-team discipline, not something that happens for free.

Intermediate How do you handle routing across multiple independently-deployed micro-frontends so the URL bar and browser history behave like one cohesive app?

Typically, one "shell" or "host" application owns the top-level router and overall page chrome (nav, header); each route maps to loading a specific remote micro-frontend's exposed component into a designated slot in the shell's layout. The remotes themselves generally shouldn't own top-level browser routing — they render into wherever the shell places them, and if a remote needs internal sub-routing of its own (nested routes within its section), it typically uses the shell's router instance (passed down) rather than instantiating a second, competing router, which would otherwise fight the shell for control of the URL and browser history.

4. Advanced questions

Advanced How do you achieve CSS isolation between micro-frontends built by different teams, potentially with different styling approaches (one team uses SASS/BEM, another uses CSS-in-JS)?

This is the same global-CSS-collision problem from the CSS guide, amplified across team boundaries with potentially different tooling entirely. Options, in increasing isolation strength: (1) strict naming convention discipline (BEM with a mandatory per-team namespace prefix) — cheapest, but relies entirely on discipline holding across teams who may not even share a lint config; (2) CSS Modules per micro-frontend, so each team's class names are hashed/scoped at build time regardless of naming convention; (3) Shadow DOM, wrapping each micro-frontend's rendered output in genuine browser-level style encapsulation — the strongest guarantee, immune to any global CSS regardless of what any other team does, at the cost of extra complexity for anything that needs to intentionally share styling (a common design system) across that boundary. For a design-system-governed product (tying back to the Design Patterns & Architecture guide), CSS Modules combined with a shared, versioned design-system package for anything that must look identical across MFEs is usually the pragmatic middle ground.

Advanced How do teams cross-communicate between micro-frontends without tightly coupling their internal implementations?

The anti-pattern to avoid is one MFE directly importing another's internal state/store — that recreates tight coupling and defeats independent deployability (a breaking internal change in one MFE now breaks another team's code with no warning). Common patterns instead: a shared, versioned event bus/pub-sub mechanism where MFEs emit and listen for well-defined, documented events (trade:selected) without knowing anything about each other's internals; or a shared, minimal global store (holding only genuinely cross-cutting state like the current user/session, not feature-specific state) that every MFE can read but each team's own feature state stays private to their MFE. The underlying principle is the same "explicit public API, private internals" boundary discussed in the Design Patterns & Architecture guide, just enforced across independently-deployed applications instead of within one codebase.

5. Expert-level & scenario-based

Expert Scenario: Team A deploys a breaking change to a shared component their micro-frontend exposes, and Team B's micro-frontend (which consumes it via Module Federation) breaks in production immediately, with no warning. How do you prevent this systemically?

This is the direct micro-frontend analog of the shared-component-library breakage scenario in the Design Patterns & Architecture guide, but worse — because Module Federation resolves at runtime, a breaking change can propagate to consumers the instant it's deployed, with no build-time warning at all (Team B's own CI never even ran against the new version). Systemic fixes: (1) treat every exposed module as a versioned, semantically-versioned public contract, with an explicit deprecation policy — never silently change an exposed module's shape; (2) pin consumer-side remote versions explicitly rather than always resolving "latest," so a remote update is an opt-in action by the consuming team, not an automatic, unreviewed runtime surprise; (3) add contract/integration tests that run the actual composed application (host + real remotes) in CI before either team's deploy, catching a breaking change before it reaches production rather than after; (4) real-time production monitoring with fast rollback (from the CI/CD guide) as the last line of defense when the above still misses something. The core lesson: runtime composition is powerful specifically because it decouples deploys, but that same decoupling is what makes an explicit contract and pinned versions non-negotiable — without them, "independent deployment" becomes "unreviewed breaking changes across team boundaries."

6. Common mistakes & debugging

Frequent review comments Always resolving remotes to "latest" instead of pinning versions, turning every remote deploy into an unreviewed breaking-change risk for consumers; letting remotes instantiate their own competing router instead of using the shell's; no CSS isolation strategy at all across teams with different styling conventions, causing style leakage; tightly coupling MFEs by directly importing each other's internal store/state instead of a well-defined shared event/contract boundary; adopting micro-frontends before the team/organizational scale genuinely justifies the added deployment and coordination complexity (the premature-adoption point from the System Design guide).

7. Frequently asked at top product companies

  • Platform/architecture-focused companies: "Walk through how Module Federation actually resolves a shared dependency at runtime" — tests real mechanical understanding, not just buzzword familiarity.
  • Staff/principal-level style: "How would you design contract testing between independently-deployed micro-frontends to prevent breaking changes reaching production?"
  • General senior-level: "How do you keep styling consistent across micro-frontends built by different teams?"

8. Cheat sheet / quick revision

Concept One-line recall
Module Federation Runtime code sharing across independently-deployed apps, no build-time compile-together step
Shared deps Version-negotiated at runtime — dedupes React etc. when versions are compatible
Routing Shell/host owns top-level routing; remotes render into slots, reuse the shell's router for sub-routes
CSS isolation Naming convention → CSS Modules → Shadow DOM, increasing isolation strength
Cross-MFE communication Event bus or minimal shared store — never direct internal-state imports
Breaking-change risk Pin versions, treat exposed modules as versioned public contracts, add contract tests
