HTML5 Interview Guide

Semantic markup, forms, storage APIs, and the structural decisions that make everything downstream — accessibility, SEO, performance — easier or harder.

1. Overview

HTML5 questions in a senior interview rarely test raw syntax — they test whether semantic markup and web platform primitives are a genuine habit, since so much of accessibility and SEO is "free" if you reach for the right element from the start, and expensive to retrofit later. This guide focuses on the areas that keep surfacing at the senior level: semantics, forms, and the storage/offline APIs.

2. Basic questions

Basic Why use <nav>, <article>, <section> instead of just <div> everywhere?

Semantic elements communicate document structure and meaning to browsers, search engines, and assistive technology — a screen reader can announce "navigation landmark" or let a user jump directly to the <main> content, none of which is possible with an undifferentiated tree of <div>s. They also give you meaningful hooks for styling and testing without inventing custom class names for structure that HTML already has a word for.

Basic <section> vs <article> vs <div> — what's the actual distinction?

<article> is for self-contained content that would make sense distributed/syndicated on its own (a blog post, a news story, a single product card). <section> groups thematically related content, typically with its own heading, but isn't necessarily standalone. <div> carries no semantic meaning at all — reach for it only when neither of the above (nor any other semantic element) fits, purely for styling/layout grouping.

Basic What does <!DOCTYPE html> actually do?

It tells the browser to render the page in standards mode rather than "quirks mode" — a legacy compatibility mode that emulates old, non-standard rendering behavior from 1990s browsers (different box-model math, different CSS parsing quirks). Omitting it, or getting it wrong, can trigger quirks mode and produce inconsistent, hard-to-debug layout behavior across browsers.

3. Intermediate questions

Intermediate localStorage vs sessionStorage vs cookies vs IndexedDB — how do you choose?
Capacity Lifetime Sent to server? Best for
Cookies ~4KB Configurable expiry Yes, every request (unless flagged otherwise) Auth tokens needing server visibility (esp. httpOnly)
localStorage ~5-10MB Until explicitly cleared No Small, non-sensitive client-only preferences
sessionStorage ~5-10MB Until tab closes No Per-tab transient state (a multi-step form draft)
IndexedDB Much larger, browser-dependent Until explicitly cleared No Structured/large client-side data, offline-first apps

Common mistake: storing an auth token in localStorage for convenience — it's readable by any JS running on the page, making it directly vulnerable to XSS in a way an httpOnly cookie is not (covered further in the Security guide).

Intermediate How does native HTML form validation work, and when do you still need JavaScript validation on top of it? 
<input type="email" required minlength="5" />

Attributes like required, type="email", pattern, min/max trigger the browser's built-in validation UI and the Constraint Validation API (element.validity, element.checkValidity()) with zero JS. This is good for basic format checks and free accessibility (announced correctly by screen readers, works without JS at all). You still need JS/server-side validation for anything the native attributes can't express — cross-field validation (password confirmation matching), async checks (username availability), and — critically — server-side validation is non-negotiable regardless, since client-side validation of any kind can be bypassed entirely by a direct API call.

Grouping related fields

<fieldset> groups related form controls together, with <legend> providing a caption a screen reader announces before reading any control inside — e.g. wrapping a set of radio buttons for "delivery method" in a fieldset means each option is announced as "delivery method: standard" instead of just "standard," which is otherwise ambiguous out of context.

Intermediate <script> loading: plain vs defer vs async — what's the timeline difference?
Attribute Blocks HTML parsing? Execution order Runs when
Plain <script src> Yes — parsing pauses until downloaded and executed In document order Immediately, wherever it appears
defer No — downloads in parallel with parsing In document order, guaranteed After the DOM is fully parsed, before DOMContentLoaded
async No — downloads in parallel with parsing Not guaranteed — whichever finishes downloading first runs first As soon as it's downloaded, which can interrupt parsing mid-way

Practical rule: use defer for your main application bundle (order matters, and it shouldn't block the initial render) — this is exactly what bundlers/frameworks inject by default. Reserve async for independent, order-agnostic scripts like analytics tags that don't need to coordinate with anything else on the page.

Intermediate <img> vs a CSS background-image — when does the choice actually matter?

An <img> is content — it's part of the accessibility tree, takes an alt attribute screen readers announce, is indexed by search engines, and supports native lazy-loading via loading="lazy" with zero JS. A CSS background-image is presentation — invisible to screen readers and search engines, and not natively lazy-loadable (the browser doesn't defer background images the way it can defer <img>). Rule of thumb: if the image conveys real content or meaning (a product photo, a chart, a user's avatar), use <img> with meaningful alt text; if it's purely decorative (a repeating texture, a decorative gradient overlay), CSS background-image is the correct, more honest choice.

4. Advanced questions

Advanced What's the difference between Canvas and SVG, and how would you choose for a data visualization in a trading dashboard?
Canvas SVG
Model Pixel-based, immediate-mode drawing — no per-shape DOM nodes Retained-mode — every shape is a real, inspectable/stylable DOM node
Performance at high element counts Better — thousands of points render without DOM overhead Degrades — thousands of DOM nodes gets expensive
Interactivity / accessibility Manual — no built-in per-shape events or ARIA Native — each element supports events, CSS, ARIA directly

For a high-density real-time price chart with thousands of updating points, Canvas (or WebGL for even higher volume) usually wins on raw rendering performance. For a dashboard with a moderate number of interactive, individually-styleable/accessible chart elements (a bar chart with tooltips per bar), SVG's DOM-native interactivity is usually the better trade-off.

Advanced What is the critical rendering path, at a summary level?

The sequence the browser follows to turn HTML/CSS/JS into pixels: parse HTML into the DOM, parse CSS into the CSSOM, combine them into a render tree (visible elements only, with computed styles), layout (compute exact position/size of everything), paint (fill in pixels), and composite (layers combined on screen via the GPU). Anything blocking this pipeline early — a render-blocking <script> in the <head>, an unoptimized CSS file — directly delays first paint. For the full mechanics (including reflow/repaint costs and why animating certain CSS properties is cheaper than others), see the Browser Internals guide.

Advanced How do Web Workers help with a CPU-heavy frontend task, and what are the constraints?

A Web Worker runs JS on a genuinely separate OS thread, communicating with the main thread only via message passing (postMessage/onmessage) — no shared memory or direct DOM access. This is the browser-side equivalent of Node's worker_threads (from the Node.js guide): offload a CPU-intensive computation (parsing/transforming a very large dataset client-side, complex client-side calculations) to a worker so the main thread stays free to keep the UI responsive. The constraint: workers can't touch the DOM directly, so any UI update based on the worker's result still has to flow back through a message to the main thread.

5. Expert-level & scenario-based

Expert Scenario: "Your team's Lighthouse accessibility score is low. Walk through your first 5 fixes."

In rough priority order: (1) semantic landmarks — swap div-soup for <header>/<nav>/<main>/<footer> so assistive tech can navigate the page structurally; (2) alt text audit — every meaningful <img> gets a real description, purely decorative ones get alt="" so they're skipped, not announced by filename; (3) color contrast — run an automated contrast check (Lighthouse flags this directly) and fix any text/background combination below WCAG AA's 4.5:1 ratio; (4) focus order and visible focus states — confirm the DOM/tab order matches the visual order, and that outline: none hasn't been removed without a replacement focus style; (5) form label associations — every input has a properly linked <label for>, with ARIA reserved only for the cases native semantics genuinely can't express. This ordering front-loads the fixes that are both high-impact and typically fast to ship, before moving into slower, more experiential fixes (full keyboard-flow testing, screen-reader walkthroughs).

Expert Scenario: an internal audit finds your app's forms are unusable with a screen reader, despite passing an automated accessibility scan. What HTML-level issues would you specifically check first?

Automated scanners catch missing <label> associations and missing alt text, but miss experiential issues: whether error messages are programmatically associated with their field (aria-describedby pointing at the error text, not just visually positioned nearby), whether the DOM order matches the visual/tab order (a CSS-only reorder can visually look right while confusing a screen reader following DOM order), whether required-field indicators are conveyed to assistive tech and not just via a red asterisk, and whether focus moves sensibly after a validation error (ideally to the first invalid field). This is the same automated-vs-manual-testing gap covered in the Accessibility guide — form UX in particular is where that gap shows up most concretely.

6. Common mistakes & debugging

Frequent review comments Div-soup instead of semantic elements, losing free accessibility/SEO structure; storing sensitive tokens in localStorage; relying only on client-side form validation with no server-side enforcement; missing or mismatched <label for>/input id pairs; images without meaningful alt text (or decorative images missing alt="", forcing screen readers to announce the filename).

7. Frequently asked at top product companies

  • General senior-level: "Why would you use semantic HTML over a div-based layout, concretely?" — tests whether it's a real habit or lip service.
  • Performance-focused companies: "When would you use a Web Worker, and what can't it do?"
  • Data-viz-heavy companies (relevant to your dashboard background): "Canvas or SVG for this chart, and why?"

8. Cheat sheet / quick revision

Concept One-line recall
Semantic elements Free structure for accessibility, SEO, and readability
localStorage Never for sensitive tokens — readable by any JS on the page
Native form validation Free UX + accessibility, but never a substitute for server-side checks
Canvas vs SVG Canvas scales to huge element counts; SVG gives native per-element interactivity
Web Workers True parallel thread for CPU work — no DOM access, message-passing only
