JavaScript (ES6+) Interview Guide

Everything from closures to the event loop to hand-rolled polyfills — the language layer under every React interview question you'll get.

1. Technology overview

JavaScript is a single-threaded, event-driven, prototype-based language with a non-blocking I/O model built on an event loop. For a 12-year React specialist, interviewers use JS questions to test two things: whether you understand what's happening underneath the frameworks you use daily, and whether you can reason precisely about asynchronous code — since almost every production bug you've debugged (race conditions, stale closures in `useEffect`, memory leaks) traces back to one of the fundamentals below.

2. Basic questions

Basic What's the difference between var, let, and const?
What

var is function-scoped and hoisted with an undefined initialization. let and const are block-scoped and hoisted into a "temporal dead zone" (TDZ) — accessing them before declaration throws a ReferenceError instead of silently returning undefined. const additionally forbids reassignment of the binding (not deep immutability of the value).

Why it matters

Block scoping is what makes closures inside loops behave correctly — the classic interview trap below depends on this. 

for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0); // 3, 3, 3
}
for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log(j), 0); // 0, 1, 2
}

var creates one shared binding across all iterations; let creates a fresh binding per iteration.

Common mistakes

Saying "const makes objects immutable" — it only locks the reference, not the object's contents (Object.freeze is needed for that, and only shallowly).

Follow-up

"What is the TDZ and why does it exist?" — it exists so that let/const catch usage-before-declaration bugs that var hides.

Basic Explain hoisting.
What

Before execution, the JS engine scans each scope and allocates memory for variable and function declarations — this is hoisting. function declarations are hoisted fully (name + body), var is hoisted as undefined, and let/const/class are hoisted but left in the TDZ.

Real-world example

Function declarations can be called before their textual position; function expressions and arrow functions assigned to const cannot.

Common mistakes

Thinking hoisting "moves code to the top" — nothing moves; only the declaration's memory allocation happens early, not the assignment.

Basic What is an Execution Context, and how does it relate to the Call Stack?
What

An execution context is the environment in which JS code is evaluated — it tracks variables, function declarations, and the value of this for that specific chunk of code. There are three types: the global execution context (created once, when the script first runs), a function execution context (created fresh every time a function is called), and an eval execution context (rare in practice). Each one is created in two phases: a creation phase (hoisting happens here — memory is allocated for variables/functions before any code runs) followed by an execution phase (code actually runs line by line).

How it connects to the Call Stack

The call stack is simply the stack data structure that tracks which execution context is currently running. Calling a function pushes a new execution context onto the stack; returning from it pops that context off. The engine always executes whatever context sits on top of the stack. 

function multiply(a, b) { return a * b; }
function square(n) { return multiply(n, n); }
function printSquare(n) { console.log(square(n)); }
printSquare(5);
// Stack grows: global → printSquare → square → multiply
// Stack unwinds in reverse as each function returns
Follow-up

"What is a Stack Overflow?" — the call stack has a fixed size; a function that keeps calling itself without a base case (uncontrolled recursion) keeps pushing new contexts until the stack's memory limit is exceeded, throwing a RangeError: Maximum call stack size exceeded.

Basic What is a closure?
What

A closure is a function bundled with references to its surrounding (lexical) scope, so it keeps access to those variables even after the outer function has returned. 

function makeCounter() {
  let count = 0;
  return () => ++count;
}
const counter = makeCounter();
counter(); // 1
counter(); // 2
Real-world example

Every custom React hook that keeps internal state between calls (before useState existed, module-level closures were how you'd memoize expensive calculations), debounced event handlers, and private-variable patterns all rely on closures.

Common mistakes

Not recognizing that closures capture variables, not values — this is exactly the var-in-loop bug above.

Follow-up

"Can closures cause memory leaks?" — yes, if a closure holds a reference to a large object (e.g. a DOM node) that's never released because the closure itself is long-lived (an event listener that's never removed). "What's the difference between scope and a closure?" — scope is the general rule for where a variable is visible; a closure is the specific, concrete result of a function "remembering" the variables from its scope even after the outer function has finished executing.

Basic What are the types of scope in JavaScript, and what's the difference between lexical scope and the scope chain?
What

Three types: global scope (declared outside any function/block, accessible everywhere), function scope (variables declared with var are visible anywhere inside the enclosing function, regardless of nested blocks), and block scope (let/const are confined to the nearest { }, including if/for blocks — this is exactly why the var-in-loop bug from the earlier question happens: var ignores the loop's block entirely).

Lexical scope vs scope chain

Lexical scope means a function's available variables are determined by where it's written in the source code, not where it's called from. The scope chain is the mechanism that enforces this at lookup time: when a variable isn't found in the current scope, the engine walks outward through each enclosing lexical scope until it's found (or throws a ReferenceError at the global scope). 

const outer = 'outer-value';
function a() {
  const inner = 'inner-value';
  function b() {
    console.log(inner, outer); // walks the scope chain outward to find both
  }
  b();
}
Common mistakes

Confusing lexical (static, determined at write-time) scope with dynamic scope (which JS doesn't have) — this is also why arrow functions' this is "lexical": it's resolved the same way a variable lookup would be, by walking outward through the enclosing scope, not by how the function is called.

Basic Difference between == and ===?

== performs type coercion before comparing ('5' == 5 is true); === compares both type and value with no coercion. Production code should default to ===; the only common accepted use of == is x == null to check for both null and undefined at once.

Basic What are truthy/falsy values?

Falsy: false, 0, -0, 0n, '', null, undefined, NaN. Everything else is truthy — including '0', [], and {}, which trips people up in conditionals.

3. Intermediate questions

Intermediate Explain the event loop, call stack, and task queues.
What

JS runs on a single call stack. Async work (timers, I/O, promises) is delegated to the browser/Node APIs; when it completes, its callback is placed on a queue. The event loop's only job is: run the stack to empty, then pull the next callback in. There are two queues that matter: the microtask queue (Promise callbacks, queueMicrotask) and the macrotask queue (setTimeout, DOM events, I/O). After every single macrotask, the engine drains the entire microtask queue before moving to rendering or the next macrotask. 

console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
console.log('4');
// Output: 1, 4, 3, 2
Why it matters

This is the single most-asked JS conceptual question at product companies because it directly explains bugs like "why did my state update render before my API call resolved."

Common mistakes

Saying "promises run immediately" — the executor runs synchronously, but .then() callbacks are always deferred to the microtask queue, even for an already-resolved promise.

Intermediate What is prototypal inheritance? How do Object.create(), constructor functions, and ES6 classes relate to it?
What

Every object has an internal [[Prototype]] link (accessible via Object.getPrototypeOf or the legacy __proto__) to another object it delegates lookups to. When you access a property, the engine walks this prototype chain until it finds the property or reaches null. 

function Animal(name){ this.name = name; }
Animal.prototype.speak = function(){ return `${this.name} makes a sound`; };
const dog = new Animal('Rex');
dog.speak(); // found via prototype chain, not own property
Three ways to set up the same inheritance

Object.create() builds an object with a specific prototype directly, with no constructor function involved at all: const dog = Object.create(animalProto). Constructor functions (above) use new plus a shared .prototype object. ES6 class syntax is sugar over the exact same constructor-function mechanism — class Dog extends Animal sets Dog.prototype.__proto__ = Animal.prototype under the hood, and super(...) inside a subclass constructor calls the parent's constructor before this can be used. 

class Animal {
  constructor(name) { this.name = name; }
  speak() { return `${this.name} makes a sound`; }
}
class Dog extends Animal {
  speak() { return `${super.speak()} (a bark, specifically)`; }
}
const rex = new Dog('Rex');
rex instanceof Animal;        // true — walks the prototype chain
rex.hasOwnProperty('name');   // true — set directly on the instance in the constructor
rex.hasOwnProperty('speak');  // false — speak lives on Dog.prototype, not the instance
__proto__ vs prototype

These are two different things that are easy to conflate: prototype is a property that exists only on functions (including classes) — it's the object that instances created with new will link to. __proto__ exists on every object (including function objects themselves) and is the actual live link to that object's own prototype. So rex.__proto__ === Dog.prototype is true, but rex.prototype is undefined (instances don't have their own .prototype).

Common mistakes

Using for...in to iterate an object's properties without a hasOwnProperty check — it also picks up enumerable properties inherited from the prototype chain, not just the object's own properties.

Intermediate Explain this binding rules.

Resolved in this priority order: new binding (constructor call → new object), explicit binding (call/apply/bind), implicit binding (called as obj.method() → this is obj), then default binding (plain function call → undefined in strict mode, global object otherwise). Arrow functions have no own this — they lexically inherit it from the enclosing scope, which is exactly why arrow functions are the default choice for React class-method-style callbacks and array callbacks.

Intermediate call() vs apply() vs bind() — what's the difference?

All three explicitly set what this refers to inside a function, but differ in when the function runs and how arguments are passed:

Method Invokes immediately? Arguments
call(thisArg, a, b, c) Yes Passed individually, comma-separated
apply(thisArg, [a, b, c]) Yes Passed as a single array
bind(thisArg, a, b) No — returns a new function Individually; can be partially applied and called later 
function greet(greeting, punctuation) {
  return `${greeting}, ${this.name}${punctuation}`;
}
const user = { name: 'Kamlesh' };
greet.call(user, 'Hi', '!');           // 'Hi, Kamlesh!' — runs now
greet.apply(user, ['Hi', '!']);        // same, args as an array
const greetUser = greet.bind(user, 'Hi'); // returns a new function, not yet run
greetUser('!');                        // 'Hi, Kamlesh!' — runs when called

Common mistake: reaching for apply out of habit when the spread operator (fn(...args)) now covers most of the "pass an array as arguments" use case that apply used to be needed for.

Intermediate Promises vs async/await — what's actually different?

Nothing at the mechanism level — async/await is syntactic sugar over promises; an async function always returns a promise, and await pauses execution of that function (not the whole thread) until the awaited promise settles. The practical difference is readability and error handling: await lets you use plain try/catch instead of chained .then/.catch, but it's easy to accidentally serialize independent async calls with sequential awaits when they should run in parallel via Promise.all. 

// Bad: sequential, ~2x slower
const user = await fetchUser();
const posts = await fetchPosts();

// Good: parallel
const [user, posts] = await Promise.all([fetchUser(), fetchPosts()]);
Intermediate How do you create a Promise from scratch, and what are its lifecycle states?
Lifecycle

A Promise starts pending, and settles exactly once into either fulfilled (via resolve()) or rejected (via reject()) — it can never change state again after settling, and any .then/.catch attached later still fires with that same final result. 

function delay(ms, value) {
  return new Promise((resolve, reject) => {
    if (ms < 0) return reject(new Error('negative delay'));
    setTimeout(() => resolve(value), ms);
  });
}

delay(1000, 'done')
  .then(result => { console.log(result); return result.toUpperCase(); })
  .then(upper => console.log(upper))   // chaining: each .then gets the previous return value
  .catch(err => console.error(err))
  .finally(() => console.log('cleanup, runs either way'));
Why chaining works

Each .then() returns a brand-new promise wrapping whatever its callback returns — a plain value gets auto-wrapped in a resolved promise, and if the callback returns another promise, the chain "flattens" and waits on it automatically. This is what lets you chain .then calls sequentially instead of nesting callbacks.

Common mistakes

Forgetting to return inside a .then() callback that itself does async work — without the return, the outer chain doesn't actually wait for that inner promise, and the next .then fires prematurely with the wrong value.

Intermediate What's the difference between debouncing and throttling?

Debounce delays execution until a pause in events (fires once, after the burst ends) — used for search-as-you-type or resize-end handlers. Throttle guarantees execution at most once per fixed interval, regardless of how many events fire — used for scroll position tracking or button-click spam prevention. Full implementations are in the coding section below.

4. Advanced questions

Advanced Walk through exactly how Promise.all, Promise.race, Promise.allSettled, and Promise.any differ, including failure semantics.
Method Resolves when Rejects when
Promise.all All promises fulfill Any one rejects (fails fast)
Promise.allSettled All settle (fulfilled or rejected) Never — always resolves with a status array
Promise.race First promise to settle (fulfilled) First promise to settle (rejected)
Promise.any First one to fulfill Only if all reject (AggregateError)

In production, allSettled is the right choice for dashboards that fetch from multiple independent widgets/APIs where one failure shouldn't blank the whole page.

Advanced How does garbage collection work, and how do memory leaks happen in a long-running SPA?
Stack vs Heap

Primitives (numbers, strings, booleans, etc.) are stored on the stack — fixed-size, fast to allocate/deallocate, and copied by value on assignment. Objects, arrays, and functions live on the heap — a much larger, less structured memory region — and variables referencing them hold a pointer to that heap location, which is why assigning an object to a new variable copies the reference, not the object itself.

How the GC decides what to collect

Older engines used reference counting (collect an object once nothing points to it anymore) — simple, but it fails on circular references (two objects referencing each other stay "referenced" forever even if nothing else points to either). V8 uses mark-and-sweep instead: starting from a set of roots (the global object, the current call stack, active closures), the engine marks every object reachable by following references, then sweeps away anything left unmarked — this correctly collects circular references that are unreachable from any root, unlike naive reference counting.

Where leaks actually come from in a SPA

Leaks typically come from: (1) event listeners attached to window/document never removed on unmount, (2) timers (setInterval) not cleared, (3) closures capturing large objects held by a long-lived cache, (4) detached DOM nodes still referenced from JS after removal from the tree. In React specifically, this is why every useEffect that subscribes to something must return a cleanup function.

Advanced What are WeakMap and WeakSet, and when would you reach for them over Map/Set?

A regular Map/Set holds a strong reference to its keys/values — an object used as a key stays alive in memory as long as the Map itself exists, even if nothing else in the app references it anymore. WeakMap/WeakSet hold weak references instead: if an object key has no other references left, the garbage collector is free to reclaim it, and the entry is automatically removed — closing exactly the kind of leak the mark-and-sweep question above describes. 

const cache = new WeakMap();
function process(domNode) {
  if (cache.has(domNode)) return cache.get(domNode);
  const result = expensiveComputation(domNode);
  cache.set(domNode, result);
  return result;
}
// If domNode is later removed from the DOM and has no other references,
// its cache entry is automatically eligible for garbage collection —
// a regular Map would keep it (and the DOM node) alive forever.

Trade-off: WeakMap/WeakSet keys must be objects (not primitives), and they're deliberately not iterable — you can't list their contents or get a size, since entries can disappear at any time via GC. Use them specifically for metadata/caching tied to an object's lifetime; use regular Map/Set for everything else.

Advanced Explain currying and partial application, with a real use case.

Currying transforms f(a, b, c) into f(a)(b)(c) — each call returns a new function until all arguments are supplied. It's useful for building specialized functions from general ones, e.g. a generic validate(rule, value) curried into validateRequired = validate('required') reused across form fields. 

const curry = fn => (...args) =>
  args.length >= fn.length
    ? fn(...args)
    : (...more) => curry(fn)(...args, ...more);

const add3 = curry((a, b, c) => a + b + c);
add3(1)(2)(3); // 6
add3(1, 2)(3); // 6

5. Expert-level & scenario-based

Expert Scenario: A production dashboard occasionally shows stale data from a previous API call after the user rapidly switches tabs. Diagnose and fix.
Diagnosis

Classic race condition: tab A's fetch is slower than tab B's, and resolves after the user has already switched, overwriting B's fresher data with A's stale response.

Fix options

1) Track a request ID/ref and ignore responses that don't match the latest request. 2) Use AbortController to cancel the in-flight request when the tab changes. 3) If using React Query/SWR, this is handled for you via automatic cancellation and query keys. 

useEffect(() => {
  const controller = new AbortController();
  fetch(url, { signal: controller.signal })
    .then(res => res.json())
    .then(setData)
    .catch(err => { if (err.name !== 'AbortError') throw err; });
  return () => controller.abort();
}, [url]);
Expert Output-based: what does this log, and why? 
async function foo() {
  console.log('A');
  await null;
  console.log('B');
}
console.log('start');
foo();
console.log('end');
// start, A, end, B

The function body runs synchronously up to the first await — so 'A' logs immediately. await then yields control back to the caller (queuing the rest as a microtask), so 'end' logs before 'B', even though await null has "nothing to wait for."

6. Coding challenges (with approach, complexity, follow-ups)

Problem: implement debounce
function debounce(fn, delay) {
  let timer;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

Time: O(1) per call. Space: O(1). Follow-up: add a cancel() method and an immediate (leading-edge) flag. Common mistake: using an arrow function for the returned function, which breaks `this` binding for object-method use cases.

Problem: implement throttle
function throttle(fn, limit) {
  let inThrottle = false;
  return function (...args) {
    if (!inThrottle) {
      fn.apply(this, args);
      inThrottle = true;
      setTimeout(() => (inThrottle = false), limit);
    }
  };
}

Follow-up: implement the trailing-edge variant that also fires once more after the window closes if a call was suppressed.

Problem: deep clone an object (handling nested objects/arrays, not circular refs) 
function deepClone(obj) {
  if (obj === null || typeof obj !== 'object') return obj;
  if (Array.isArray(obj)) return obj.map(deepClone);
  return Object.fromEntries(
    Object.entries(obj).map(([k, v]) => [k, deepClone(v)])
  );
}

Follow-up: "How would you handle circular references?" — keep a WeakMap of already-cloned source objects to their clones and return the cached clone when re-encountered. Mention structuredClone() as the modern built-in that already does this.

Problem: polyfill Array.prototype.flat(depth) 
function flatten(arr, depth = 1) {
  return depth > 0
    ? arr.reduce((acc, val) =>
        acc.concat(Array.isArray(val) ? flatten(val, depth - 1) : val), [])
    : arr.slice();
}
Problem: polyfill Promise.all
function promiseAll(promises) {
  return new Promise((resolve, reject) => {
    const results = [];
    let completed = 0;
    if (promises.length === 0) return resolve(results);
    promises.forEach((p, i) => {
      Promise.resolve(p).then(val => {
        results[i] = val;
        if (++completed === promises.length) resolve(results);
      }).catch(reject);
    });
  });
}

Time: O(n). Common mistake: pushing results in resolution order instead of indexing by original position — order must match input, not completion time.

Problem: implement your own bind
Function.prototype.myBind = function (ctx, ...boundArgs) {
  const fn = this;
  return function (...args) {
    return fn.apply(ctx, [...boundArgs, ...args]);
  };
};

7. Common mistakes & debugging

Watch for these in your own code review comments Mutating state directly instead of creating new references (breaks React's shallow-compare); comparing objects/arrays with === and expecting deep equality; forgetting await inside a .map() (returns an array of pending promises, not results — use Promise.all(arr.map(async ...))); relying on for...in on arrays (iterates enumerable keys including inherited/non-index ones — use for...of or array methods).

8. Frequently asked at top product companies

  • Amazon/Google style: "Implement an LRU cache" (tests Map + doubly linked list, not JS trivia — but framed as a JS coding round).
  • Meta style: Output-based questions stacking closures + event loop + hoisting in one snippet.
  • Microsoft/Adobe style: "Polyfill Array.prototype.reduce" or "Function.prototype.call."
  • Uber/Airbnb style: Debounce/throttle from scratch, then asked to adapt it live for a new requirement (e.g. "now make it cancelable").
