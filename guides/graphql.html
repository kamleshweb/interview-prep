GraphQL Interview Guide

Schema-first API design, the over/under-fetching problem it solves, the N+1 problem it introduces, and how client-side caching actually differs from REST's.

1. Overview

GraphQL is a query language and runtime for APIs where the client specifies exactly what data shape it needs in a single request, resolved against a strongly-typed schema on the server. It's not a replacement for REST everywhere — it solves a specific problem (client-driven, flexible data shapes for complex UIs) at the cost of some genuine trade-offs (caching complexity, a new class of performance problem). Interviewers care whether you understand those trade-offs concretely, not just that GraphQL exists.

2. Basic questions

Basic What problem does GraphQL actually solve over REST?

Two related problems: over-fetching (a REST endpoint returns a fixed shape — if you only need a user's name, you still get their entire profile object) and under-fetching (a single view needs data from several REST endpoints, requiring multiple round-trips, or a custom aggregating endpoint built just for that one screen). GraphQL lets the client specify precisely which fields it needs, across what would otherwise be several REST resources, in a single request — a genuinely different fit for UIs with many different views each needing a different data slice from the same underlying entities.

Basic Query vs Mutation vs Subscription — what's each for?

Query: read data (the GraphQL equivalent of a REST GET). Mutation: write/modify data (equivalent of POST/PUT/PATCH/DELETE) — mutations execute sequentially, one at a time, even when multiple are sent in one request, specifically so that side-effecting operations don't race each other. Subscription: a long-lived connection (typically over WebSockets) that pushes updates to the client whenever the subscribed data changes — the real-time equivalent, used for live updates rather than the client polling repeatedly.

Basic What's a GraphQL schema, and what problem does its strong typing solve?

The schema is a contract, written in GraphQL's Schema Definition Language, declaring every type, field, and its exact type (including nullability) available in the API — the single source of truth both client and server code-generation tools can rely on. This is what enables tooling like GraphQL Codegen (mentioned in the TypeScript guide) to generate accurate client-side types directly from the schema, closing the "hand-typed API response drifts from reality" gap that plain REST + hand-written types is prone to.

3. Intermediate questions

Intermediate Explain the N+1 query problem and how it's typically solved. 
query {
  trades {        # 1 query to fetch all trades
    id
    counterparty { # naive resolver: 1 additional query PER trade
      name
    }
  }
}

If the resolver for counterparty naively runs its own database query every time it's called, fetching 100 trades triggers 1 query for the trades plus 100 more (one per trade) for their counterparties — the "N+1" problem. The standard fix is a DataLoader pattern: within a single request, batch all the individual counterparty lookups that were triggered during that tick into one combined query (WHERE id IN (...)) and cache the results per request, so 100 trades cost 2 queries total instead of 101. This is a server-side/resolver-implementation concern, but it's frequently asked of frontend candidates too since understanding it explains why a poorly-implemented GraphQL API can be slower than the REST equivalent it replaced.

Intermediate Why is GraphQL caching harder than REST caching, and how does Apollo Client's normalized cache address it?

REST's HTTP caching (covered in the REST APIs guide — ETags, Cache-Control) works because each GET request has a stable, predictable URL identifying exactly one resource. GraphQL typically sends all requests as POST to a single endpoint with a query body that varies per call — there's no stable URL for an HTTP cache/CDN to key on. Apollo Client instead maintains its own normalized, in-memory cache: every object returned by any query is stored by its type + ID (e.g. Trade:t4521), so if two different queries both return data about the same trade, they share one cached entry — updating it in one place (e.g. after a mutation) automatically reflects everywhere that trade is displayed, without needing a full refetch.

Intermediate What are GraphQL fragments, and why do they matter for a component-based UI? 
fragment TradeRowFields on Trade {
  id
  notional
  ccyPair
  status
}

query TradeList {
  trades { ...TradeRowFields }
}

A fragment declares a reusable set of fields, typically colocated with the React component that actually needs them — the TradeRow component owns and declares exactly the fields it renders, and a parent query composes fragments from all its children rather than a screen-level query awkwardly listing every descendant's fields in one place. This keeps data requirements colocated with the component that uses them (similar in spirit to colocating styles/logic with components) instead of a top-level query becoming a dumping ground that's hard to trace back to what actually needs each field.

4. Advanced questions

Advanced How would you implement optimistic UI updates for a GraphQL mutation, and what happens if the mutation fails?

Apollo Client (and similar clients) let a mutation call specify an optimisticResponse — a client-predicted result applied to the cache immediately, before the server actually responds, so the UI updates instantly (marking a trade as "confirmed" the moment the user clicks, rather than waiting on the round-trip). If the real server response later differs from the optimistic guess, the cache reconciles to the real data; if the mutation fails outright, the client rolls the cache back to its pre-optimistic state. This is the same pattern discussed for REST APIs' concurrency handling — the interesting design decision is what the user sees during that rollback (a toast explaining the action failed and reverted, not a silent, confusing snap-back).

5. Expert-level & scenario-based

Expert Scenario: a single dashboard query has grown to request dozens of fields across deeply nested relationships, and it's now slow and hard to reason about. How do you fix this at the API/architecture level?

This is the GraphQL-specific version of "one screen's needs bloated a shared contract." Fixes: (1) split the mega-query into fragments colocated per component (as above) so each piece's cost is visible and attributable, rather than one opaque top-level query; (2) add query complexity/depth limiting on the server so a single query can't recursively traverse arbitrarily deep relationships unbounded — a common real production safeguard, and also a security consideration (an unbounded nested query is a potential denial-of-service vector); (3) consider whether some of the deeply nested data actually needs to load eagerly with the rest, or could be deferred to a separate, lazily-triggered query once the user actually expands that section of the UI (the GraphQL equivalent of code-splitting a data requirement, not just a JS bundle).

6. Common mistakes & debugging

Frequent review comments Not batching resolver-level data access, causing N+1 query storms; treating GraphQL as a drop-in replacement for every REST endpoint rather than reserving it for genuinely complex, flexible-shape UI needs; giant, un-fragmented top-level queries that make it impossible to tell which component needs which field; no query depth/complexity limiting, leaving the API open to expensive or abusive nested queries; assuming the normalized cache "just works" without understanding cache-key collisions when types lack a stable, unique ID field.

7. Frequently asked at top product companies

  • General senior-level: "When would you choose GraphQL over REST for a new feature, and when would you not?" — tests genuine trade-off reasoning, not a blanket preference.
  • Backend-leaning interviewers: "Explain the N+1 problem and how you'd fix it" — near-universal for any GraphQL-touching role.
  • Data-viz/dashboard-heavy companies (relevant to your background): "How would you keep a dashboard's GraphQL query maintainable as more widgets are added over time?" — tests fragment colocation reasoning.
