Design Patterns & Frontend Architecture Interview Guide

Reusable component patterns (compound components, render props, provider pattern) and the organizational patterns that keep a large app maintainable as a team grows — the "how do you structure things" questions senior/lead interviews lean on heavily.

1. Overview — two related but distinct skill areas

Design patterns here means reusable solutions to recurring component-design problems in JS/React — not always the classic Gang-of-Four patterns verbatim, but their spirit adapted to a component-tree, hooks-based world. Frontend architecture is the layer above individual components: how code is organized across files/folders/repos, how teams avoid stepping on each other, and how a codebase stays navigable at 100,000+ lines. Interviewers ask about both because a candidate at the 12-year/lead level is expected to make these calls for a team, not just for their own PRs.

2. Design patterns — basic

Basic What's the "composition over inheritance" principle, and why does React lean on it so heavily?

React deliberately has no class-inheritance-based component reuse mechanism (you never extend one component from another to reuse UI logic) — instead, you build complex components by composing smaller ones together (nesting, passing components as props/children). This avoids the classic inheritance problem of a deep, fragile hierarchy where a change to a base class ripples unpredictably through every subclass — composition keeps each piece independently understandable and swappable.

Basic Container/Presentational pattern — is it still relevant with hooks?

The classic split — a "container" component owns data/logic, a "presentational" component only renders UI from props — predates hooks, which now let you extract the logic into a custom hook instead of a wrapping container component. The underlying principle (separate "what data/logic" from "how it looks") is still exactly right and still asked about; the mechanism has just shifted from container components to custom hooks + purely presentational components consuming them.

3. Design patterns — intermediate

Intermediate Explain the Compound Components pattern with a real example.
What

A set of components that work together implicitly, sharing state via Context, giving the consumer flexible control over layout while the components manage their own coordination internally — much like native <select> and <option>.

<Tabs defaultValue="summary">
  <Tabs.List>
    <Tabs.Trigger value="summary">Summary</Tabs.Trigger>
    <Tabs.Trigger value="trades">Trades</Tabs.Trigger>
  </Tabs.List>
  <Tabs.Panel value="summary">...</Tabs.Panel>
  <Tabs.Panel value="trades">...</Tabs.Panel>
</Tabs>
Why

The consumer can reorder, omit, or insert extra markup between the sub-components freely — far more flexible than a single monolithic <Tabs tabs={[...]} /> prop-driven API, while Tabs still owns the actual active-tab state internally via Context, so consumers don't have to wire that up themselves.

Intermediate Render Props vs Custom Hooks — is the render props pattern dead? 
// Render props (older pattern)
<MousePosition render={({ x, y }) => <span>{x}, {y}</span>} />

// Custom hook (modern equivalent)
function Cursor() {
  const { x, y } = useMousePosition();
  return <span>{x}, {y}</span>;
}

Custom hooks solve the exact same problem (sharing stateful logic without a wrapper component) with less nesting and better composability — you can combine multiple hooks freely, whereas nesting several render-prop components creates the notorious "callback hell"-style pyramid. Render props aren't strictly dead — some library APIs still use them for genuinely render-time flexibility (e.g. a virtualization library needing to control exactly what gets rendered per row) — but for sharing logic, hooks have almost entirely replaced them.

Intermediate The Provider Pattern — when is it the right tool, and when is it overused?

Wrapping a subtree in a Context Provider is right for genuinely cross-cutting, infrequently-changing values consumed deep in the tree without prop-drilling — theme, current user, locale, feature flags. It's overused when reached for as a general state-management solution for frequently-changing data (as covered in the Redux guide, every value change re-renders every consumer with no built-in selector granularity) — that's a sign a dedicated state library or moving the state lower in the tree is the better fit.

4. Design patterns — advanced

Advanced Explain the "state reducer pattern" and why a component library author might expose it. 
function useToggle({ reducer = defaultReducer } = {}) {
  const [state, dispatch] = useReducer(reducer, { on: false });
  const toggle = () => dispatch({ type: 'TOGGLE' });
  return { on: state.on, toggle };
}

// Consumer can override the default behavior for one specific case
function customReducer(state, action) {
  if (action.type === 'TOGGLE' && state.locked) return state; // block toggling
  return defaultReducer(state, action);
}
useToggle({ reducer: customReducer });

Instead of a component library trying to anticipate every possible customization with more and more props (prop explosion), the state reducer pattern hands the consumer the actual state-transition logic to override, letting them intercept or modify specific transitions without forking the component. This is an advanced, library-author-facing pattern — most product-code interviews won't require you to build one from scratch, but recognizing it (and explaining why it beats endless boolean props) signals real component-API design maturity.

Advanced Design a reusable, flexible Modal API — what are the competing concerns, and how do you balance them?

Competing concerns: simplicity for the common case (one line to open a confirm dialog) vs flexibility for complex cases (a modal with custom footer actions, size variants, nested modals). A layered API often resolves this well: a simple imperative helper (confirm({title, message})) built on top of a more flexible compound-component API (<Modal><Modal.Header/><Modal.Body/><Modal.Footer/></Modal>) for anything beyond the common case — so 90% of call sites use the simple helper, and the remaining 10% aren't blocked by it. Also worth naming: focus trap and return-focus-on-close (from the Accessibility guide), and a single global modal root/portal so z-index and stacking-context bugs don't accumulate across the app.

5. Frontend architecture — structuring a large codebase

Architecture Feature-folder structure vs type-folder structure — which do you recommend, and why? 
// Type-folder (organized by what kind of file it is)
/components  /hooks  /reducers  /services

// Feature-folder (organized by what part of the product it is)
/features/trades/{components,hooks,api,slice}.js
/features/reconciliation/{components,hooks,api,slice}.js

Type-folder structure scales poorly past a small app — working on one feature means jumping across four or five top-level folders, and it's hard to tell what's safe to delete when a feature is removed. Feature-folder structure keeps everything related to one part of the product together, makes ownership boundaries between teams visible in the file tree itself, and lets you delete a whole feature by deleting one folder. Shared, truly cross-feature code (design-system components, generic utilities) still gets its own top-level /shared or /common folder — the goal isn't zero shared code, it's making the exception explicit rather than the default.

Architecture How do you enforce module boundaries so features don't quietly become tangled with each other as a team grows?

File structure alone is a convention, not an enforcement mechanism — nothing stops someone importing directly from another feature's internals. Enforce it with lint rules (e.g. eslint-plugin-boundaries or path-based import restrictions) that fail CI if features/trades imports directly from features/reconciliation/internal/... instead of through an explicit public entry point (each feature exporting only what it wants to expose via an index.js). This turns "please don't do that" tribal knowledge into a build failure, which scales far better across a 10+ engineer team than code-review vigilance alone.

Architecture Monorepo vs polyrepo for multiple related frontend apps — trade-offs?
MonorepoPolyrepo
Shared code changesOne atomic commit/PR across app + shared libRequires publishing a new package version and bumping it in each consumer separately
ToolingNeeds investment (Nx/Turborepo/Lerna) for fast, selective buildsSimpler individually, but cross-repo refactors are painful and easy to leave inconsistent
Team autonomyShared CI/lint/versioning conventions across teamsEach team fully owns their own release cadence and tooling choices

For closely related apps sharing a design system and frequently coordinated releases (typical of a large product suite under one org), a monorepo with proper build-caching tooling usually wins on developer experience once the initial tooling investment is made. For genuinely independent products/teams with little shared code, the coordination overhead of a monorepo may not be worth it.

6. Expert-level & scenario-based

Expert Scenario: your team's shared component library keeps breaking downstream product teams whenever a component's internal behavior changes, even without an intentional breaking API change. How do you fix the underlying process?

This is usually a symptom of an implicit, undocumented contract — consuming teams depend on incidental behavior (exact DOM structure for their own CSS overrides, a specific re-render timing) that was never part of the component's declared public API. Fixes: (1) explicitly document and version the actual public API (props, slots, exposed CSS variables) and treat anything else as a private implementation detail that can change without a major version bump; (2) add visual-regression testing (Chromatic or similar) to the library's CI so unintended visual changes are caught before publishing, not after a downstream team notices in production; (3) adopt semantic versioning strictly and give consuming teams a deprecation window for anything that must change, rather than silent behavior shifts in a patch release.

7. Common mistakes & debugging

Frequent review comments Reaching for a generic pattern (HOC, render props, provider) out of habit instead of matching the pattern to the actual problem; type-folder structure that forces every feature change to touch five unrelated top-level folders; shared component libraries with no enforced public API, so downstream teams depend on internals that then can't safely change; premature micro-frontend or monorepo adoption before the team/product scale actually justifies the tooling overhead.

8. Frequently asked at top product companies

  • General senior/lead style: "Design a reusable Table/Modal/Form component API that multiple teams will consume" — tests compound components + prop-API design judgment together.
  • Staff-level style: "How would you restructure a 5-year-old codebase that's become hard to navigate, without a full rewrite?" — expects an incremental strategy (introduce boundaries/lint rules, migrate feature-by-feature) rather than a big-bang answer.
  • Leadership-adjacent (relevant to your 12 years mentoring teams): "How do you get buy-in from a team to adopt a new architectural convention?" — tests whether you can drive change beyond your own code, not just design it.
