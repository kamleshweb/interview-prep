Next.js Interview Guide

Rendering strategies, the App Router's Server/Client Component split, data fetching, and the performance wins Next.js gives you over a plain client-rendered React SPA.

1. Technology overview

Next.js is a React framework that adds file-system-based routing, multiple rendering strategies (SSR, SSG, ISR, client rendering), and a built-in build/runtime pipeline (bundling, image optimization, API routes) on top of React. It exists because a plain client-rendered SPA ships a blank HTML shell and does all rendering in the browser — bad for SEO and slow "time to first paint" on a content-heavy site. At the senior level, interviewers care whether you can correctly choose which rendering strategy fits a given page, and whether you understand the App Router's Server Components model well enough to avoid shipping unnecessary client JS.

2. Basic questions

Basic What problem does Next.js solve that a plain Create-React-App style SPA doesn't?

A pure client-rendered SPA sends a near-empty HTML file; the browser has to download, parse, and execute the JS bundle before anything meaningful appears — bad for SEO crawlers that don't execute JS well, and bad for perceived performance on slow connections/devices. Next.js renders HTML on the server (or at build time) so the browser gets meaningful content immediately, then "hydrates" it with React to make it interactive. It also removes the need to hand-roll routing, code-splitting, and bundling configuration.

Basic SSR vs SSG vs ISR vs CSR — what's the actual difference?
Strategy When HTML is generated Best for
CSR (client-side rendering) In the browser, after JS loads Highly interactive, non-SEO-critical views (internal dashboards)
SSR (server-side rendering) On every request, on the server Pages needing fresh, per-request data (a user's account page)
SSG (static generation) Once, at build time Content that rarely changes (marketing pages, docs)
ISR (incremental static regen.) At build time, then re-generated in the background after a set interval Mostly-static content that changes occasionally (a product catalog)

Common mistake: defaulting every page to SSR "to be safe" — this adds server load and latency to pages that don't need per-request freshness; picking the right strategy per route is the actual skill being tested.

Basic What is hydration, and why can it cause a "flash" or console warning?

Hydration is React attaching event listeners and internal state to the server-rendered HTML in the browser, without re-creating the DOM from scratch. A "hydration mismatch" warning happens when the server-rendered markup and the client's first render don't match exactly (e.g. using Date.now() or Math.random() directly in render, or checking typeof window to conditionally render something) — React then has to discard and rebuild the mismatched portion, which can cause a visible flash and defeats the purpose of SSR.

3. Intermediate questions

Intermediate Explain Server Components vs Client Components in the App Router — this is the most important conceptual shift from Pages Router.
What

In the App Router, every component is a Server Component by default: it renders on the server (or at build time), never ships its own JS to the browser, and can directly access backend resources (databases, file system, secrets) without an API layer. Add the 'use client' directive at the top of a file to opt a component (and everything it imports) into being a Client Component — one that hydrates in the browser and can use hooks, state, effects, and browser APIs. 

// app/trades/page.jsx — Server Component (default, no directive needed)
async function TradesPage() {
  const trades = await db.trades.findMany(); // direct data access, no API round-trip
  return <TradeTable trades={trades} />;
}

// TradeTable.jsx
'use client';
function TradeTable({ trades }) {
  const [sortBy, setSortBy] = useState('date'); // needs client interactivity
  // ...
}
Why it matters

Server Components ship zero JS for anything that's purely presentational or read-only — for a large enterprise dashboard, this can meaningfully shrink the client bundle by keeping data-fetching, formatting, and static layout on the server, and only marking the genuinely interactive leaves (sortable headers, editable cells, filters) as Client Components.

Common mistake

Slapping 'use client' on a high-level layout component "just in case" — because the directive propagates to everything imported beneath it, this silently converts an entire subtree back into client-rendered JS, defeating the whole benefit.

Intermediate How does data fetching work in the App Router compared to getServerSideProps/getStaticProps in the Pages Router?

Pages Router: each page file exports a special function (getServerSideProps for per-request SSR, getStaticProps for build-time SSG, optionally with revalidate for ISR) that Next.js calls before rendering the page. App Router: Server Components fetch data directly with async/await inside the component itself — no special exported function — and caching/revalidation behavior is controlled via fetch options ({ cache: 'force-cache' | 'no-store', next: { revalidate: 60 } }) rather than a separate API.

Intermediate What are API routes / Route Handlers, and when would you use one instead of calling your backend directly from the client?

Route Handlers (app/api/.../route.js) let you write backend endpoints inside the Next.js app itself. Use them when: you need to hide an API key/secret that can't be exposed to the browser, you need to aggregate/transform data from multiple backend services before sending a single response to the client, or you need a webhook endpoint. For a straightforward "call our existing REST API," calling it directly from a Server Component (or via a typed client) is usually simpler than adding an extra hop through a Next.js API route.

4. Advanced questions

Advanced How does Next.js's built-in image optimization actually improve performance, and what are the trade-offs?

next/image automatically serves correctly-sized, modern-format (WebP/AVIF) images based on the requesting device's viewport, lazy-loads images below the fold by default, and prevents layout shift by requiring explicit width/height (reserving space before the image loads — directly improving Cumulative Layout Shift, a Core Web Vital). Trade-off: it requires either Next.js's own image optimization API (adds a server/edge processing cost per unique size requested) or a configured external loader (e.g. Cloudinary/Imgix) for full control in a self-hosted or CDN-heavy setup.

Advanced Explain Next.js Middleware and a realistic enterprise use case.

Middleware runs at the edge, before a request completes, and can rewrite, redirect, or modify the response — before any page or API route code executes. A realistic use case for an enterprise banking-style app: reading an auth cookie in middleware and redirecting unauthenticated users to /login for any route under /dashboard, without needing every single Server Component to duplicate that check — while still treating it as a UX layer, not a substitute for real server-side authorization on the actual data endpoints.

5. Expert-level & scenario-based

Expert Scenario: you're migrating an internal financial dashboard (heavy client interactivity — grids, real-time price ticks, role-based editing) from a CRA-style SPA to Next.js. Which pages benefit from SSR/SSG, and which should stay effectively client-rendered?

Not every page benefits equally. Pages with genuinely static or slow-changing shell content (a landing/help page, a static report template) are good SSG/ISR candidates. A logged-in-only trade blotter with per-request, per-user, permission-filtered data is a reasonable SSR candidate for the initial data (skip an extra client-side loading spinner on first load), but the live-updating, highly interactive grid itself (WebSocket ticks, inline editing, virtualization) is inherently a Client Component — there's no SEO or first-paint benefit to server-rendering data that's about to be overwritten by a live feed a second later. The honest answer in an interview: identify each page's actual requirement (SEO? first-paint speed? auth-gated? real-time?) rather than assuming "Next.js means everything should be SSR now."

Expert Output-based: why does this Server Component throw a runtime error, and what's the fix? 
// app/trades/page.jsx (Server Component, no 'use client')
function TradesPage() {
  const [filter, setFilter] = useState('all'); // Error: useState in a Server Component
  return <div>{filter}</div>;
}

Server Components render on the server (or at build time) and never re-render on the client in response to interaction — there's no "instance" of them living in the browser to hold state, so React hooks that depend on client-side lifecycle (useState, useEffect, event handlers) simply aren't available there. The fix is to extract the interactive piece into its own file with 'use client' at the top, and pass server-fetched data into it as props.

6. Common mistakes & debugging

Frequent review comments Adding 'use client' too high in the tree, converting large subtrees back to client-rendered JS unnecessarily; using SSR by default for pages that don't need per-request freshness, adding needless server load; causing hydration mismatches with non-deterministic render output (random IDs, current time) without guarding them behind a client-only effect; fetching data client-side with useEffect inside what could've been a Server Component, re-introducing the render-then-fetch waterfall Next.js is meant to avoid.

7. Frequently asked at top product companies

  • Vercel-adjacent/startup style: "Explain when you'd choose SSR vs SSG vs ISR for three different pages of the same app" — always a scenario question, not a definition question.
  • General senior-level: "What's the difference between a Server Component and 'server-side rendering' — aren't they the same thing?" (They're related but distinct: SSR is about when HTML is generated; Server Components are about where a component's code runs and whether its JS ships to the client at all.)
  • Performance-focused companies: "How would you reduce a Next.js app's client bundle size?" — Server Components for non-interactive subtrees, dynamic import() for heavy client-only libraries, and auditing third-party script usage.

8. Cheat sheet / quick revision

Concept One-line recall
SSR HTML generated per request, on the server
SSG HTML generated once, at build time
ISR Static + periodic background regeneration
Server Component (default) Renders server-side, ships zero JS to the browser
Client Component 'use client' — hydrates, can use hooks/state/events
Hydration mismatch Server & first client render disagree — usually non-deterministic output
Middleware Runs at the edge before the route — good for auth redirects, not data authorization
