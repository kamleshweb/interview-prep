Redux / Redux Toolkit Interview Guide

Predictable state at scale — actions, reducers, middleware, normalization, and why Redux Toolkit replaced hand-written Redux almost everywhere.

1. Technology overview

Redux is a predictable state container: a single store, a pure reducer function that computes the next state from the current state and an action, and a strict unidirectional data flow (dispatch → reducer → new state → re-render). Redux Toolkit (RTK) is the officially recommended way to write Redux today — it wraps the same core with createSlice, built-in Immer for "mutating" syntax that produces immutable updates, createAsyncThunk for async flows, and RTK Query for data fetching/caching. For a banking/data-heavy dashboard (trade blotters, reconciliation views), Redux's selector-based subscriptions are what let large tables re-render only the rows that actually changed.

2. Basic questions

Basic What are the three core principles of Redux?

1) Single source of truth — the whole app state lives in one store/object tree. 2) State is read-only — the only way to change it is to dispatch an action describing what happened. 3) Changes are made with pure functions — reducers take (state, action) and return a new state without mutating the input or causing side effects.

Basic What is a reducer, and why must it be pure?

A reducer is (state, action) => newState. It must be pure (no API calls, no Date.now()/Math.random(), no mutation of its arguments) because Redux relies on this purity for predictability, time-travel debugging (replaying actions must always produce the same result), and for React-Redux's ability to detect changes via reference equality — mutating state in place means the reference never changes, so connected components silently fail to re-render. 

// Wrong — mutates state
function reducer(state, action) {
  state.items.push(action.payload); // BUG: same reference returned
  return state;
}
// Right — returns a new reference
function reducer(state, action) {
  return { ...state, items: [...state.items, action.payload] };
}
Basic What does createSlice give you over hand-written Redux?

createSlice generates action creators and action types automatically from a set of reducer functions, and lets you write "mutating" logic inside each case reducer (state.value += 1) because it wraps the whole thing in Immer under the hood — Immer produces a new immutable state from your mutation-style code via a structural-sharing draft object. This eliminates almost all of the original boilerplate (separate action type constants, switch statements, manual spread operators).

3. Intermediate questions

Intermediate Why does Redux need middleware at all — what problem does it solve?

Reducers must be pure and synchronous, but real apps need side effects (API calls, logging, analytics). Middleware sits between dispatch and the reducer, intercepting every action, so it's the sanctioned place to run async logic, log actions, or even dispatch further actions — without breaking reducer purity. redux-thunk lets an action creator return a function (given dispatch/getState) instead of a plain object, so you can dispatch "pending/fulfilled/rejected" actions around an API call. 

const fetchTrades = () => async (dispatch, getState) => {
  dispatch({ type: 'trades/loading' });
  try {
    const data = await api.getTrades();
    dispatch({ type: 'trades/success', payload: data });
  } catch (err) {
    dispatch({ type: 'trades/error', payload: err.message });
  }
};
Intermediate Thunks vs Sagas vs RTK Query — how do you choose?
Tool Model Best for
Thunk Plain async functions Simple, imperative async flows — most CRUD apps
Saga Generator-based effects, declarative & testable Complex flows: debounced search, cancellation, race conditions, sequencing multiple sagas — common in large trading UIs with WebSocket streams
RTK Query Declarative data-fetching + caching layer Standard "fetch and cache server data" — replaces most hand-written thunks entirely

Modern guidance: use RTK Query for server-state (the vast majority of API calls) and keep thunks/sagas only for genuinely complex orchestration RTK Query doesn't model well (e.g. reacting to a WebSocket stream and coordinating several dependent dispatches).

Intermediate How do selectors work, and why does reselect/RTK's createSelector matter for performance?

A selector is just a function that reads a slice of state: selectTrades = state => state.trades.list. The problem appears with derived data — selectSortedTrades = state => [...state.trades.list].sort(...) creates a brand-new array on every call, so a component subscribed via useSelector re-renders every time any unrelated state changes, even though the actual sorted content didn't change. createSelector memoizes on its input selectors' outputs — the sort only re-runs when state.trades.list itself changes by reference, not on every store update.

4. Advanced questions

Advanced Explain state normalization and why it matters for a trade/reconciliation table.
What

Instead of storing nested arrays of objects, normalize into a flat lookup: an ids: string[] array plus an entities: { [id]: Trade } map (this is exactly what RTK's createEntityAdapter generates for you). 

// Nested (harder to update one trade efficiently)
{ trades: [{ id: 't1', ccy: 'USD' }, { id: 't2', ccy: 'EUR' }] }

// Normalized
{ ids: ['t1', 't2'], entities: { t1: { id: 't1', ccy: 'USD' }, t2: { id: 't2', ccy: 'EUR' } } }
Why

Updating a single trade in the nested shape means finding it in an array and rebuilding the whole array (O(n), and it changes the array reference so every consumer of the list re-renders). In the normalized shape, updating one entity only changes that one key in the map — the ids array reference is untouched, so components that only care about the list order don't re-render on a single trade's price tick.

Advanced How does React-Redux's useSelector decide whether to re-render, and how do you avoid unnecessary re-renders?

useSelector subscribes to the store and re-renders whenever the selector's return value is not === (by default, reference equality) to its previous return value, on every dispatched action. Two common mistakes: (1) returning a new object/array literal from the selector (state => ({ a: state.a, b: state.b })) — this is a new reference on every single dispatch, so the component re-renders on unrelated actions too; fix by either splitting into multiple useSelector calls or using createSelector/a shallow-equality comparator. (2) Selecting more of the state than the component needs — always select the narrowest slice possible.

5. Expert-level & scenario-based

Expert Scenario: a live reconciliation dashboard receives WebSocket price ticks for thousands of trades per second. The Redux store updates on every tick and the whole grid stutters. How do you redesign the state/update flow?

1) Normalize entities so a tick only touches one entity's key, not a whole array reference. 2) Batch incoming ticks — buffer them for one animation frame and dispatch a single batched update instead of one action per tick (Redux itself batches renders inside React event handlers, but raw WebSocket callbacks fire outside that batching in older React versions, so you may need unstable_batchedUpdates or rely on React 18's automatic batching). 3) Make row components subscribe to their own entity via a memoized per-id selector (createSelector factory pattern) so a tick for trade t500 only re-renders that row, not the table. 4) Consider whether every tick needs to hit Redux at all — for extremely high-frequency data, some teams keep the "live" price in local component state or a ref updated via a subscription, and only sync into Redux at a throttled interval for anything that needs global visibility (audit/reporting).

Expert Output-based: what's wrong with this slice, and how would RTK Query replace it? 
const tradesSlice = createSlice({
  name: 'trades',
  initialState: { list: [], loading: false, error: null },
  reducers: {},
  extraReducers: builder => {
    builder
      .addCase(fetchTrades.pending, state => { state.loading = true; })
      .addCase(fetchTrades.fulfilled, (state, action) => {
        state.loading = false;
        state.list = action.payload; // no caching, no dedup, no invalidation
      });
  }
});

This hand-written thunk slice has no request de-duplication (calling fetchTrades() twice fires two network requests), no cache invalidation strategy, and no automatic refetch-on-focus/reconnect. RTK Query's createApi + useGetTradesQuery() gives you all of that for free — caching by query key, automatic loading/error states, and tag-based invalidation (e.g. invalidate the Trades tag after a mutation so the list refetches automatically) — replacing this entire slice with a few lines of endpoint definition.

6. Coding challenge

Problem: write a Redux Toolkit async thunk with proper loading/error state handling 
// slice.js
import { createSlice, createAsyncThunk } from '@reduxjs/toolkit';

export const fetchUser = createAsyncThunk('user/fetch', async (userId) => {
  const res = await fetch(`/api/users/${userId}`);
  if (!res.ok) throw new Error('Failed to fetch user');
  return res.json();
});

const userSlice = createSlice({
  name: 'user',
  initialState: { data: null, status: 'idle', error: null },
  reducers: {},
  extraReducers: builder => {
    builder
      .addCase(fetchUser.pending, state => { state.status = 'loading'; state.error = null; })
      .addCase(fetchUser.fulfilled, (state, action) => {
        state.status = 'succeeded';
        state.data = action.payload; // Immer allows this "mutation" syntax safely
      })
      .addCase(fetchUser.rejected, (state, action) => {
        state.status = 'failed';
        state.error = action.error.message;
      });
  },
});

export default userSlice.reducer;

Explanation: createAsyncThunk auto-generates pending/fulfilled/rejected action types from the single async function you give it; extraReducers handles each declaratively instead of you hand-writing three separate action creators and matching switch cases. Immer lets you write state.data = ... even though the reducer actually returns a brand-new, immutable state object under the hood via structural sharing.

Common mistakes: forgetting to reset error back to null in the pending case — a stale error from a previous failed attempt stays visible during a retry, even though the retry hasn't failed yet; selecting the whole slice in useSelector (useSelector(state => state.user)) instead of the specific field actually needed (useSelector(state => state.user.data)) — causes re-renders on every field change in the slice, not just the one the component reads; not memoizing derived selectors built on top of this state.

Follow-up: "How would you cancel a stale thunk if the user navigates away before it resolves?" — three options: call .unwrap() and catch the rejection from navigating away, wire an AbortController into the thunk's fetch call and abort it in a cleanup function, or use RTK Query instead, which handles request cancellation on unmount natively without any of this manual wiring.

7. Architecture questions

  • "How do you structure Redux state for a large app with 10+ feature teams?" — feature-folder slices (one slice per domain, colocated with the feature, not a single giant reducers folder), RTK Query for all server-state so feature teams stop hand-rolling loading/error booleans, and a documented convention for what belongs in Redux vs local component state vs URL state.
  • "When would you NOT use Redux at all?" — small apps, or apps where most state is genuinely local/UI-only (form inputs, modal open/closed) — Context or plain useState/useReducer is simpler and avoids the overhead of wiring every value through the global store.

8. Common mistakes & debugging

Frequent review comments Mutating state directly inside a hand-written reducer (outside createSlice's Immer wrapper, this silently breaks change detection); creating new object/array references inside useSelector without memoization; storing derived/computed data in the store instead of computing it in a memoized selector (leads to state going out of sync); dispatching too many fine-grained actions per user interaction instead of one well-modeled action; treating useMemo/useCallback as free when memoizing selector results — they carry their own comparison cost, so only reach for them where they solve a measured problem.

9. Frequently asked at top product companies

  • Amazon/Google style: "Design the Redux state shape for a shopping cart / order system" — tests normalization instincts directly.
  • Meta/Uber style: "Walk through what happens, in order, from a component calling dispatch to the DOM updating" — tests middleware chain → reducer → store subscription → React-Redux re-render → reconciliation, end to end.
  • Fintech-style (relevant to your background): "How would you keep a Redux-backed grid in sync with a real-time market data feed without janking the UI?"
