React Router Interview Guide

Client-side routing, nested layouts, data loading, guarded routes, and the trade-offs of SPA routing vs full page navigation.

1. Technology overview

React Router is the de facto client-side routing library for React SPAs. It intercepts navigation (link clicks, back/forward, programmatic navigation) using the History API and renders the matching component tree without a full page reload. Modern versions (v6.4+/v7 "data routers") also own data loading/mutations per route (loader/action), blurring the line between "router" and "framework." For an enterprise dashboard with role-gated sections (e.g. a trade blotter only certain roles can edit), the interesting questions are less about basic route matching and more about nested layouts, protected routes, and code-splitting per route.

2. Basic questions

Basic How does client-side routing actually work without hitting the server for every navigation?

The router listens to the browser's History API (pushState/replaceState/popstate). Clicking a <Link> calls event.preventDefault() on the native anchor click, then calls history.pushState to change the URL bar without a network request, and the router's internal state update triggers React to render whatever component is registered for the new path. The server is only ever hit again on a hard refresh or a direct URL entry — which is why SPA routing requires server-side (or CDN) fallback configuration to always serve index.html for unknown paths, or deep links 404.

Basic <Link> vs a plain <a> tag — why does it matter?

A plain <a href> triggers a full browser navigation — the entire app unmounts, JS re-downloads/re-parses, and all client state is lost. <Link> intercepts the click and performs the in-app transition described above, preserving the SPA's loaded state (e.g. Redux store, in-memory caches) for anything outside the unmounted route.

Basic How do you read a dynamic segment like /trades/:tradeId? 
<Route path="/trades/:tradeId" element={<TradeDetail />} />

function TradeDetail() {
  const { tradeId } = useParams();
  // fetch or select trade by tradeId
}

3. Intermediate questions

Intermediate Explain nested routes and layout routes — why are they better than manually composing layout components? 
<Route path="/dashboard" element={<DashboardLayout />}>
  <Route index element={<Overview />} />
  <Route path="trades" element={<Trades />} />
  <Route path="trades/:tradeId" element={<TradeDetail />} />
</Route>

function DashboardLayout() {
  return (
    <div>
      <Sidebar />
      <Outlet />  {/* renders whichever child route matched */}
    </div>
  );
}

Nested routes co-locate the URL structure with the component tree structure — the shared sidebar/header only mounts once and stays mounted across child-route navigation, instead of every "page" component re-importing and re-rendering its own copy of the layout. This also means layout-level state (an open sidebar section, a scroll position) survives navigating between child routes.

Intermediate How do you implement a protected/role-gated route? 
function RequireAuth({ roles, children }) {
  const { user } = useAuth();
  const location = useLocation();
  if (!user) {
    return <Navigate to="/login" state={{ from: location }} replace />;
  }
  if (roles && !roles.some(r => user.roles.includes(r))) {
    return <Navigate to="/403" replace />;
  }
  return children;
}

<Route path="/trades/:id/edit" element={
  <RequireAuth roles={['trader']}><EditTrade /></RequireAuth>
} />

Why replace matters: using replace instead of a normal push means the redirected-from URL doesn't sit in browser history, so hitting "back" after login doesn't bounce the user back into the guard. Why pass state={{ from: location }}: so the login page can redirect back to where the user was actually headed, not always to a hardcoded dashboard.

Common mistake

Treating a client-side route guard as real security — it only hides UI. The actual authorization check must also happen server-side on every API call; a route guard is UX, not a security boundary.

Intermediate How do you code-split by route? 
const TradeDetail = React.lazy(() => import('./TradeDetail'));

<Route path="trades/:id" element={
  <Suspense fallback={<Spinner />}><TradeDetail /></Suspense>
} />

Each route becomes its own JS chunk, fetched only when the user actually navigates there — critical for a large multi-module dashboard (FX, Rates, Commodities, Collateral) where no single user session needs every module's code upfront.

4. Advanced questions

Advanced Explain the newer data-router APIs (loader, action, useLoaderData) and how they change the fetch-on-render pattern.

Traditionally, a route component renders first (often with a loading state), then fires a useEffect to fetch data — a "render-then-fetch" waterfall. Data routers let a route declare a loader function that the router calls before rendering the component, so data-fetching starts as soon as navigation is triggered (in parallel with fetching the route's code chunk if lazy-loaded), and the component reads the result synchronously via useLoaderData() with no loading-state juggling for the initial render. 

{
  path: 'trades/:id',
  loader: ({ params }) => fetchTrade(params.id),
  element: <TradeDetail />
}
function TradeDetail() {
  const trade = useLoaderData(); // already resolved before this renders
}

action functions play the same role for mutations (form submissions) — the router calls the action, then re-runs relevant loaders to refresh data, all without manual refetch logic scattered across components.

Advanced How do you handle scroll restoration and preventing "flash of previous route" during navigation?

By default, SPA routers don't restore scroll position the way native browser navigation does. React Router ships a <ScrollRestoration /> component (data-router APIs) that stores/restores per-location scroll position, falling back to scroll-to-top on new locations. For "flash of stale content" (briefly showing the old route's UI while the new one's data loads), the fix is either the loader-based pre-fetch above, or wrapping transitions in useTransition/startTransition so React can keep showing the old UI until the new one is ready instead of an abrupt unmount/loading-spinner flash.

5. Expert-level & scenario-based

Expert Scenario: users report that deep-linking directly to /trades/T-4521 (e.g. from a shared Slack link) sometimes shows a blank page or a 404, even though the trade exists and the in-app link works fine. Diagnose.

Two most likely causes, both classic SPA-routing gaps: (1) Server-side fallback misconfiguration — the hosting layer (CDN/Nginx/S3+CloudFront) isn't rewriting unknown paths to index.html, so a direct hit to /trades/T-4521 asks the server for a resource that doesn't exist as a literal file and gets a real 404 before React Router ever loads. (2) Missing loader/guard handling for a fresh page load — code that assumes some global state (auth token already in Redux, a previously-fetched trade list already in memory) is present because it normally is when navigating within the app, but on a hard refresh/direct load that state hasn't been populated yet, so the component reads undefined and renders blank instead of triggering its own fetch. The fix for (1) is a server/CDN rewrite rule; for (2), every route that can be a valid entry point must be able to bootstrap its own required data independently, not assume it was navigated-to from within the app.

Expert Output-based: why might this route configuration cause an infinite redirect loop? 
function RequireAuth({ children }) {
  const { user, loading } = useAuth();
  if (loading) return null; // BUG
  if (!user) return <Navigate to="/login" />;
  return children;
}

If loading starts as false before the auth check has actually resolved (a common initial-state bug), user reads as null on the very first render, triggering a redirect to /login before the real auth state has loaded — then once auth resolves to a valid user, the app may redirect back, creating a loop under certain effect-ordering timings. The fix is ensuring the auth hook's initial loading state truly reflects "haven't checked yet" (true until the check completes), and rendering a loading UI — not null, and not proceeding to the redirect check — until that resolves.

6. Common mistakes & debugging

Frequent review comments Using <a href> instead of <Link>/navigate() for in-app links, causing full reloads; forgetting replace on redirect-after-login flows, polluting history; not memoizing route-level components passed inline as element={<Foo />} where Foo itself is expensive and doesn't need to remount on every parent re-render; treating route guards as a security boundary instead of a UX convenience.

7. Frequently asked at top product companies

  • Amazon/Microsoft style: "Implement a protected route wrapper with role-based access" — almost always asked as a live-coding exercise.
  • Meta/Airbnb style: "How would you preserve scroll position and avoid content flash when navigating a large list → detail page?"
  • General senior-level: "Walk through everything that happens from clicking a <Link> to the new page being interactive" — tests the full pipeline: click intercepted → pushState → route match → (optional) loader fetch → code-split chunk load → render → paint.

8. Cheat sheet / quick revision

Concept One-line recall
Client routing Intercepts clicks, uses History API, no network round-trip
Nested routes Shared layout stays mounted; <Outlet/> renders the matched child
Protected routes UX-level only — real auth must still be enforced server-side
Loaders Fetch before render, parallel with code-split chunk loading
Code splitting Lazy-load per route so users only download the modules they visit
Deep-link bugs Usually a server rewrite-rule gap or a "state assumed already loaded" bug
