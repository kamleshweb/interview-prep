Git Interview Guide

Branching strategy, rebase vs merge, and the recovery commands that separate someone who's memorized Git from someone who's actually broken and fixed a repo under pressure.

1. Overview

Git questions in a senior interview aren't really about command syntax — they're a proxy for how you work with a team: do you keep history readable, do you understand what a rebase actually does before you use it on shared branches, and can you recover from a mistake without panicking. Given 12 years and cross-team collaboration on your resume, expect scenario-based questions more than "what does git status do."

2. Basic questions

Basic What's the difference between git fetch and git pull?

git fetch downloads the remote's latest commits/branches into your local repo's remote-tracking branches (e.g. origin/main) without touching your working branch at all — safe to run anytime. git pull is fetch followed immediately by a merge (or rebase, if configured) of the fetched changes into your current branch — it actually changes your working branch, which is why pulling on a branch with uncommitted or diverged local work can trigger a merge conflict you weren't expecting.

Basic What does git rebase actually do, mechanically?

It takes the commits unique to your branch, temporarily sets them aside, moves your branch pointer to the tip of the target branch, then replays each of your commits one by one on top — producing new commits (new hashes) with the same changes but a different parent. This creates a linear history (no merge commit) but rewrites commit identity, which is exactly why rebasing commits that have already been pushed and shared is dangerous — anyone who already has the old commits now has a diverged, conflicting history.

Basic What's a fast-forward merge, and when does Git do one automatically?

If the target branch has had no new commits since your feature branch diverged from it, merging just moves the target branch's pointer forward to your branch's tip — no merge commit is created because there's nothing to actually reconcile. Once the target branch has moved on with its own new commits, a fast-forward isn't possible and Git creates a real merge commit (or requires a rebase first) to combine the two diverged histories.

3. Intermediate questions

Intermediate Merge vs rebase for integrating a feature branch — what would you actually recommend for a team, and why?
MergeRebase
HistoryPreserves exactly what happened, including a merge commitLinear, easier to read/bisect, loses the "this was a branch" record
Safety on shared branchesSafe — never rewrites existing commitsUnsafe on branches others have already pulled — rewrites history
Common conventionMerge feature branches into main via PR (keeps a clear record of what landed together)Rebase your own feature branch onto main before opening/updating a PR, to keep your branch's own history clean before it's shared

A common, safe convention: rebase freely on your own branch to clean it up before pushing/opening a PR, but always merge (never rebase) when integrating into a shared branch like main that other people have already pulled from.

Intermediate What's git cherry-pick, and give a real scenario where you'd use it?

git cherry-pick <commit-hash> applies the changes from one specific commit onto your current branch, without bringing along anything else from the source branch. Real scenario: a critical bug fix was committed to main, but a release branch already cut from an earlier point also needs that exact fix without pulling in every other unrelated commit that's landed on main since — cherry-picking the single fix commit onto the release branch is the clean way to backport it.

Intermediate How do you resolve a merge conflict, step by step, and what actually causes one?

A conflict happens when Git can't automatically reconcile the same lines of a file changed differently on both branches (or one side deleted a file the other modified). Git marks the conflicting sections in the file with <<<<<<< HEAD / ======= / >>>>>>> branch-name markers; you manually edit the file to the correct final content, remove the markers, then git add the resolved file and git commit (for a merge) or git rebase --continue (for a rebase in progress). For anything non-trivial, it's worth re-running the test suite on the resolved result before pushing — a syntactically clean resolution can still be logically wrong.

4. Advanced questions

Advanced How does git bisect work, and when is it the right tool over just reading commit history?

git bisect performs an automated binary search through commit history: you mark a known-good commit and a known-bad one, and Git checks out the midpoint for you to test; you mark it good or bad, and it narrows the range by half each time until it identifies the exact commit that introduced the regression. It's the right tool when a regression's cause isn't obvious from reading the log (dozens/hundreds of commits between the last known-good state and now, or a bug that isn't tied to any commit message mentioning the affected area) — bisecting turns "search through 200 commits" into roughly log2(200) ≈ 8 actual test cycles. Combined with git bisect run <test-script>, this can be fully automated against your test suite.

Advanced What's the difference between git reset, git revert, and git checkout/restore for undoing changes, and which is safe on a shared branch?
CommandEffectSafe on shared/pushed branches?
git reset --hard <commit>Moves the branch pointer back, discarding later commits and working directory changesNo — rewrites history; force-push required, breaks anyone else's clone
git revert <commit>Creates a NEW commit that undoes the changes of a previous commitYes — history is never rewritten, just added to
git restore <file>Discards uncommitted local changes to a specific fileN/A — only affects your local working directory

The rule of thumb interviewers want to hear: once something is pushed and others may have it, undo with revert (adds a correcting commit) rather than reset (rewrites/destroys history), unless you've explicitly coordinated a force-push with the whole team.

5. Expert-level & scenario-based

Expert Scenario: you accidentally force-pushed and overwrote three days of a teammate's commits on a shared branch. Walk through how you'd recover them.

First, don't panic and don't push again. Git rarely deletes commit data immediately — check git reflog on the machine where the force-push originated (or your own local clone if you had already fetched/pulled the branch before it was overwritten) — the reflog records every position HEAD/branches have pointed to recently, including the commit that existed before the force-push. Once you find the lost commit's hash in the reflog, you can create a new branch at that point (git branch recovery <hash>) and then merge or cherry-pick the recovered work back into the shared branch. If the reflog on the original machine has already expired (default ~90 days, but can be pruned) and no other clone has the commits, they may be genuinely unrecoverable — which is exactly the argument for protecting shared branches (branch protection rules requiring PRs, disallowing force-push) so this class of accident becomes structurally impossible rather than relying on individual carefulness.

Expert Design a branching strategy for a team of 10+ engineers shipping continuously to production, with the ability to hotfix urgently.

Trunk-based development (or a lightweight GitHub-flow variant) generally scales better for continuous delivery than long-lived Git-flow-style develop/release branches: short-lived feature branches off main, merged via PR behind feature flags if the work isn't ready to ship yet (decoupling merge from release), with main always deployable. For urgent hotfixes: branch directly off the current production tag/commit, fix, PR-review on an expedited basis, merge to main, and deploy — feature flags mean the hotfix doesn't have to wait for unrelated in-progress feature branches to also be release-ready. The trade-off to name explicitly: trunk-based development requires strong CI (fast, reliable tests) and feature-flag discipline to be safe; without those, teams often fall back to Git-flow's more isolated branches at the cost of slower integration and bigger, riskier merges.

6. Common mistakes & debugging

Frequent review comments Rebasing or force-pushing a branch other people have already pulled from, silently breaking their local history; committing generated files (build output, node_modules) due to a missing/incomplete .gitignore; giant, unreviewable PRs instead of small, incremental ones; vague commit messages ("fix", "wip") that make git blame/bisect far less useful months later; resolving a merge conflict syntactically without re-running tests, shipping a logically broken resolution.

7. Frequently asked at top product companies

  • General senior-level: "Walk through your branching strategy and why" — near-universal, especially at companies practicing continuous deployment.
  • Amazon/Google style: "How would you find which commit introduced a regression across 300 commits with no useful commit messages?" — tests git bisect directly.
  • Team-lead style (relevant to your 12 years): "A teammate keeps force-pushing to shared branches — how do you address it, both technically and as a lead?" — tests both Git knowledge (branch protection rules) and people/process judgment.
