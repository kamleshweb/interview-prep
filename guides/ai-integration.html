AI / LLM Integration Guide

Building a production chatbot feature on top of OpenAI's API — architecture, streaming, prompt engineering, cost control, and the security mistakes that matter most when an LLM is wired into a real application.

1. Overview

This is one of the fastest-growing "so tell me about a project" topics in interviews right now, and it's on your resume directly (OpenAI/ChatGPT integration — a conversational assistant feature) — expect a genuine follow-up conversation here, not just trivia. Unlike most of this site, LLM-integration questions blend frontend concerns (streaming UI, chat state, loading/error UX) with backend and security concerns (never exposing an API key client-side, rate limiting, cost control) — interviewers use this topic specifically to see whether you understand the system around the API call, not just that you can call fetch against an endpoint.

2. Basic questions

Basic Why can't you call the OpenAI API directly from the browser, and what's the correct architecture?

An API key placed in frontend code — even "hidden" in an environment variable at build time — ends up embedded in the shipped JS bundle, fully readable by anyone who opens DevTools. The correct architecture is always: browser → your own backend → OpenAI. Your backend holds the API key as a genuine server-side secret, and exposes your own endpoint (e.g. POST /api/chat) that the frontend calls instead — this is the same principle as the REST APIs and Security guides' "never ship secrets to the client" rule, just applied to an LLM key specifically. This also gives you a natural place to enforce rate limiting, logging, content moderation, and cost controls before a request ever reaches OpenAI.

Basic What does the basic request/response shape of a chat completion actually look like? 
// Your backend calls OpenAI like this
const response = await openai.chat.completions.create({
  model: 'gpt-4o',
  messages: [
    { role: 'system', content: 'You are a support assistant for a trade reporting platform.' },
    { role: 'user', content: 'Why was my trade rejected?' },
  ],
});
const reply = response.choices[0].message.content;

The messages array is the entire conversation history sent on every request — the API itself is stateless; there's no server-side session remembering earlier turns unless you're using a newer stateful API variant. This is a fairly common point of confusion: your own application is responsible for accumulating and re-sending the conversation history each time, not the LLM provider.

3. Intermediate questions

Intermediate How do you implement streaming responses so the chatbot's reply appears token-by-token instead of all at once?
Backend — proxy the stream through
// Express route
app.post('/api/chat', async (req, res) => {
  res.setHeader('Content-Type', 'text/event-stream');
  const stream = await openai.chat.completions.create({
    model: 'gpt-4o',
    messages: req.body.messages,
    stream: true,
  });
  for await (const chunk of stream) {
    const token = chunk.choices[0]?.delta?.content || '';
    res.write(`data: ${JSON.stringify({ token })}\n\n`);
  }
  res.end();
});
Frontend — consume it and append tokens as they arrive 
const res = await fetch('/api/chat', { method: 'POST', body: JSON.stringify({ messages }) });
const reader = res.body.getReader();
const decoder = new TextDecoder();
let fullText = '';

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  const chunk = decoder.decode(value);
  const token = JSON.parse(chunk.replace('data: ', '')).token;
  fullText += token;
  setMessages(prev => updateLastMessage(prev, fullText)); // re-render with each token
}

Streaming matters for perceived performance specifically — an LLM response can take several seconds to fully generate; showing tokens as they arrive (the familiar "typing" effect) makes the wait feel dramatically shorter than a blank loading spinner followed by the whole answer appearing at once, even though the total time to completion is identical either way.

Intermediate How do you manage conversation history and the context window as a chat gets long?

Every model has a maximum context window (a token budget covering the system prompt, the entire message history, and the response) — a long-running conversation will eventually exceed it, causing a request error. Common strategies, from simplest to most sophisticated: (1) a simple sliding window — keep only the last N messages, dropping the oldest; (2) periodic summarization — when the history grows past a threshold, ask the model to summarize the conversation so far into a compact system message, then continue from there instead of the full verbatim history; (3) retrieval — store the full history elsewhere (a database) and only pull in the most relevant prior messages for the current turn, rather than assuming recency is always what's relevant. For a support chatbot specifically, resetting context per session (rather than one infinitely-growing conversation) is usually the right default — it caps cost and avoids irrelevant, stale context bleeding into later questions.

Intermediate What's prompt engineering in practice, and what does a well-structured system prompt for a support chatbot actually look like? 
const systemPrompt = `You are a support assistant for a bank's trade reporting platform.
Scope: only answer questions about trade status, ACK/NACK meanings, and how to use the reconciliation dashboard.
If asked about anything outside this scope, politely redirect the user to the appropriate team.
Never invent a trade status or reference number — only state what appears in the provided context.
If you don't have enough information to answer, say so and suggest checking the dashboard directly.`;

A good system prompt does three things: constrains scope (what the assistant should and shouldn't attempt to answer), sets tone/format (concise, no unnecessary hedging, matching the product's voice), and — critically for anything touching real data — explicitly instructs the model not to fabricate specifics it wasn't given, which is the frontline defense against hallucination for a support-style assistant.

4. Advanced questions

Advanced How would you ground a chatbot's answers in real, current data instead of relying purely on the model's own knowledge (RAG, at a practical level)?

Retrieval-Augmented Generation: before calling the LLM, retrieve the actually-relevant data for the user's question (a specific trade's real status from your database, the exact rejection reason from the reconciliation system) and inject it into the prompt as context, then instruct the model to answer only from that provided context. For a support chatbot on a trade reporting platform, this might mean: parse the user's question for a trade ID, look it up via your existing REST API, and include the real record in the system/context message before the model ever generates a response — rather than asking the model to "know" trade statuses from training data, which it fundamentally can't, since that data doesn't exist anywhere in its training set and is constantly changing anyway. This is the single most important pattern for making an LLM feature trustworthy in a data-driven application — the model's job becomes summarizing/explaining real data fetched by your own code, not recalling facts from memory.

Advanced How do you control and predict the cost of an LLM-powered feature in production?

Cost scales with tokens in (the full conversation history sent every request) plus tokens out (the response length) — a naive implementation that resends an ever-growing conversation history on every turn has cost that grows roughly quadratically over a long conversation, not linearly. Concrete controls: (1) apply the context-window management strategies above (sliding window/summarization) — this is a cost lever as much as a technical necessity; (2) set an explicit max_tokens cap on responses so a single reply can't balloon unexpectedly; (3) choose the smallest model that reliably handles the task — a lighter/cheaper model for simple classification or short support answers, reserving a larger model only for genuinely complex reasoning; (4) rate-limit per user/session server-side, both for cost predictability and to prevent one user (or a bug causing a retry loop) from generating runaway spend; (5) cache identical/near-identical queries (a common FAQ-style question) rather than re-generating a fresh response every time.

Advanced What is function/tool calling, and when would you use it instead of just parsing the model's free-text response? 
const response = await openai.chat.completions.create({
  model: 'gpt-4o',
  messages,
  tools: [{
    type: 'function',
    function: {
      name: 'getTradeStatus',
      description: 'Look up the current status of a trade by ID',
      parameters: { type: 'object', properties: { tradeId: { type: 'string' } }, required: ['tradeId'] },
    },
  }],
});
// The model responds with a structured tool call instead of free text when it decides one is needed
const toolCall = response.choices[0].message.tool_calls?.[0];
if (toolCall?.function.name === 'getTradeStatus') {
  const { tradeId } = JSON.parse(toolCall.function.arguments);
  const status = await fetchTradeStatus(tradeId); // your own real API call
  // send the result back to the model as a follow-up message to generate the final natural-language reply
}

Function calling lets the model emit a structured, schema-validated request for your application to fulfill (a real database lookup, an API call) instead of trying to parse an intention out of free-form text with regex or string matching — which is exactly the fragile pattern function calling replaces. It's the standard mechanism for wiring RAG-style data lookups into a conversation cleanly: the model decides when a lookup is needed based on the user's question, your code executes the actual lookup, and the model then turns the real result into a natural-language answer.

5. Expert-level & scenario-based

Expert Scenario: your support chatbot for a banking platform confidently gives a wrong answer about a trade's status. How do you both prevent this and handle it when it happens anyway?

Prevention: the RAG pattern above — never let the model answer factual questions about specific, real, changing data from its own "knowledge"; always inject the actual current record and instruct it to answer only from that context. A well-scoped system prompt (from the intermediate section) that explicitly forbids inventing specifics is a second line of defense, not a substitute for grounding. Handling it when it happens anyway: for a regulated, financial context specifically, any AI-generated answer touching real account/trade data should be clearly labeled as AI-generated and, for anything consequential, paired with a direct link to the authoritative source (the actual trade record in the dashboard) so the user can verify rather than blindly trust the chat answer. Log every conversation (with appropriate data-scrubbing per the Security guide) so a reported bad answer can actually be investigated and used to refine the prompt or retrieval logic, rather than being an unreproducible one-off complaint.

Expert Scenario: how would you test a chatbot feature, given that LLM responses aren't deterministic the way normal application code is?

Split what you're actually testing: (1) the deterministic parts — your API integration layer, streaming logic, conversation-history management, function-calling dispatch, error/rate-limit handling — are ordinary code and testable exactly like anything else in the Testing guide (mock the OpenAI client the same way you'd mock any external API, per the MSW-vs-module-mock guidance there). (2) The model's actual output quality can't be asserted with exact-match tests since wording varies between calls — instead, evaluate a curated set of representative test prompts against criteria that don't depend on exact wording: does the response stay within scope, does it correctly refuse out-of-scope questions, does it correctly ground itself in provided context rather than inventing details, does a function call get triggered for the right kinds of questions. Some teams use a second LLM call as an automated "judge" scoring responses against these criteria at a coarse pass/fail level for regression testing across many prompts; for anything higher-stakes, periodic human review of a sample of real conversations remains necessary — this is the LLM-feature equivalent of the "automated scan misses reading order" gap the Testing and Performance & Accessibility guides describe for accessibility.

6. Common mistakes & debugging

Frequent review comments Putting the API key in frontend code or a public environment variable, exposing it in the shipped bundle; sending the entire unbounded conversation history forever, letting cost grow unchecked; no max_tokens cap, letting a single response balloon in length and cost; no rate limiting, leaving a retry loop or a single abusive user able to generate large, unexpected spend; asking the model to answer factual questions about real, current data from its own "knowledge" instead of grounding it via RAG; treating a confident-sounding response as automatically correct instead of designing for the fact that hallucination is a real, expected failure mode, not a rare edge case.

7. Frequently asked at top product companies

  • General senior-level: "Walk me through the architecture of an LLM-powered feature end to end, client to provider and back" — tests whether the API-key/proxy/streaming/cost fundamentals are second nature, not memorized.
  • Fintech-specific (directly relevant to your background): "How would you prevent a support chatbot from giving incorrect information about a customer's real account/trade data?" — tests RAG and grounding specifically.
  • Staff/Lead-level: "How would you control and forecast the cost of an AI feature before it ships, and monitor it afterward?" — tests the token-cost mechanics and rate-limiting design together.

8. Cheat sheet / quick revision

API key placement Backend only, always — never in frontend code or a public env var
