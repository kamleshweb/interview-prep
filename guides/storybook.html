Storybook Interview Guide

Component-driven development, isolating components from app context, and how Storybook becomes the backbone of a design system's documentation and visual regression testing.

1. Overview

Storybook is a tool for building and viewing UI components in isolation, outside the context of a full running app — each component is documented as one or more "stories" (a specific rendered state, given specific props/args). It matters at the senior/lead level mainly for what it enables organizationally: a living, browsable catalog of a design system, a sandbox for building components without needing the whole app's routing/data layer running, and a foundation for automated visual regression testing.

2. Basic questions

Basic What is component-driven development, and what problem does building in Storybook first solve?

Component-driven development means building UI bottom-up — starting with the smallest, most isolated pieces (a Button, an Input) and composing upward, rather than building a whole page and extracting components later. Building a component in Storybook first forces you to define its props/API in isolation, without the crutch of "it works because the page around it happens to provide the right data" — which surfaces missing edge cases (empty states, error states, very long text) far earlier than discovering them only when a real page happens to hit that scenario.

Basic What's a "story," and what are "args"? 
// Button.stories.js
export default { component: Button };

export const Primary = { args: { label: 'Save', variant: 'primary' } };
export const Disabled = { args: { label: 'Save', variant: 'primary', disabled: true } };

A story is one specific, named rendering of a component with a specific set of props ("args"). Args are Storybook's term for the props passed into that rendering — exposing them as controls in the UI lets anyone browsing Storybook (not just engineers) interactively tweak props and see the component respond live, without touching code.

3. Intermediate questions

Intermediate How do you handle a component that depends on Context (Redux store, Router, theme) inside Storybook, where none of that app-level setup exists by default? 
// .storybook/preview.js — global decorator wraps every story
export const decorators = [
  (Story) => (
    <Provider store={mockStore}>
      <ThemeProvider theme={defaultTheme}>
        <Story />
      </ThemeProvider>
    </Provider>
  ),
];

Storybook "decorators" wrap every story (or specific ones) in whatever providers the component needs — a mock Redux store with representative fake data, a Router wrapper for components using useNavigate/Link, a ThemeProvider. This is exactly the same problem the Testing guide's RTL examples solve for unit tests — Storybook needs the same kind of "fake the surrounding app context" setup, just for visual browsing instead of assertions.

Intermediate What are addons, and name a couple that matter for a design-system-focused team?

Addons extend Storybook's UI with extra panels/functionality. Ones that matter most for a design-system team: the a11y addon (runs automated accessibility checks against every story, surfacing violations right in the component-authoring workflow rather than downstream); the controls addon (auto-generates interactive prop controls from a component's TypeScript types/PropTypes); and Chromatic (technically a separate hosted service, but tightly integrated) for visual regression testing across every story.

4. Advanced questions

Advanced How does visual regression testing (Chromatic or similar) actually work, and what's the workflow when it flags a change?

On each build, every story is rendered and screenshotted (typically across multiple browsers/viewports); the new screenshots are pixel-diffed against the last-accepted baseline for that story. If any pixels differ beyond a configured threshold, the build is flagged for human review rather than auto-passing or auto-failing — because not every visual diff is a bug; some are intentional design changes. The reviewer (often the PR author or a design-system owner) either accepts the new screenshots as the new baseline (if the change was intentional) or rejects/fixes the code (if it was an accidental regression). This turns "did my change accidentally break some other component's spacing" from a manual, easy-to-miss QA pass into an automated, per-PR gate.

Advanced How would you use Storybook to help enforce a shared component library's public API discipline (referencing the Design Patterns & Architecture guide's governance concerns)?

Storybook's auto-generated docs (from TypeScript prop types/JSDoc comments) become the de facto, always-up-to-date public API reference for every component — since it's generated directly from the same types the compiler enforces, it can't silently drift out of sync with the real component the way a hand-maintained README can. Combined with Chromatic visual regression testing in CI, this gives consuming teams two concrete guarantees before a new library version ships: the documented prop API is accurate, and no existing story's visual output changed unexpectedly. That's a meaningfully stronger contract than "we wrote good docs and hope nothing broke," directly addressing the governance problem raised in the architecture guide.

5. Expert-level & scenario-based

Expert Scenario: your team's Storybook has grown to hundreds of stories and visual regression checks now take 20+ minutes in CI, slowing every PR. How do you address it?

Similar to the E2E-suite scaling problem from the Testing guide: (1) run visual regression only against stories that changed, or that belong to components whose dependency graph actually changed, rather than re-snapshotting every story on every PR unconditionally — most visual regression tools (Chromatic) support this kind of change-detection/TurboSnap-style optimization out of the box; (2) parallelize snapshot rendering across workers; (3) periodically audit and prune genuinely redundant stories (multiple stories that differ only in a prop value that doesn't meaningfully change visual output) rather than treating "more stories" as an unconditional good — story count should track meaningfully distinct states, not exhaustively enumerate every prop permutation.

6. Common mistakes & debugging

Frequent review comments Building a component directly in the app first and writing stories as an afterthought (loses the "surfaces edge cases early" benefit entirely); missing decorators for Context-dependent components, causing confusing runtime errors in Storybook that don't reflect a real component bug; treating visual regression flags as noise to auto-approve without review, defeating their purpose; letting the story count balloon with near-duplicate states instead of covering genuinely distinct, meaningful component states.

7. Frequently asked at top product companies

  • Design-system-focused companies: "How do you keep a shared component library's documentation from going stale?" — tests whether you know Storybook's docs can be type-generated rather than hand-maintained.
  • General senior-level: "How would you test that a component still looks correct after a refactor, beyond functional unit tests?" — tests visual regression testing awareness specifically.

8. Cheat sheet / quick revision

Concept One-line recall
Component-driven dev Build isolated components first — surfaces edge cases early
Story / args One named rendering with a specific prop set; args = the props themselves
Decorators Wrap stories with Context providers the component depends on
Visual regression Pixel-diff every story against a baseline; human review on any diff
Auto-generated docs Generated from real types — can't silently drift from the actual component
