TypeScript Interview Guide

Static typing on top of the JavaScript you already know — generics, utility types, and the typing patterns that show up constantly in React codebases and API layers.

1. Technology overview

TypeScript is a structurally-typed superset of JavaScript that compiles (via tsc or a transpiler like Babel/SWC) to plain JS — types exist only at compile time and are fully erased at runtime. For a senior candidate, interviewers use TypeScript questions to test whether you can model real domain data precisely (e.g. a trade/reconciliation payload with optional fields, discriminated statuses, nested arrays) and whether you understand structural typing well enough to avoid the common "any-typed escape hatch" anti-pattern under deadline pressure.

2. Basic questions

Basic What is structural typing, and how is it different from nominal typing (Java/C#)?
What

TypeScript compares types by their shape — if an object has all the properties a type requires (with compatible types), it's assignable to that type, regardless of name or declared inheritance. Nominal typing (Java, C#) requires an explicit declared relationship (implements/extends). 

interface Point { x: number; y: number; }
function log(p: Point) { console.log(p.x, p.y); }
log({ x: 1, y: 2, z: 3 }); // OK — has at least x and y (extra props allowed via inference, not object literals)
Common mistake

Assuming two differently-named interfaces with identical shapes are incompatible — they're not; TypeScript only cares about structure.

Basic interface vs type — when do you actually need one over the other?
Capability interface type
Declaration merging (reopen & extend) Yes No
Union / intersection types No Yes
Primitives, tuples, mapped/conditional types No Yes
Extending extends & intersection

Practical rule: use interface for public object shapes (component props, API response contracts) since consumers can extend them; use type for unions, tuples, and anything computed (mapped/conditional types).

Basic What does any vs unknown vs never mean?

any disables type checking entirely (escape hatch — avoid in production code). unknown is the type-safe counterpart: you can assign anything to it, but you must narrow it (via a type guard) before using it. never represents a value that can never occur — the return type of a function that always throws, or the exhaustive "impossible" branch of a discriminated union switch.

Basic What are tuples and enums, and why do many teams avoid numeric enums?
Tuples

A tuple is a fixed-length array where each position has its own specific type: [string, number] means "exactly two elements — a string then a number," unlike string[] which allows any length of strings. Useful for things like useState's return value ([value, setValue]) where position carries meaning.

Enums
enum Status { Idle, Loading, Success, Error }       // numeric — values are 0,1,2,3
enum Role { Admin = 'admin', Viewer = 'viewer' }    // string enum — safer

type Role2 = 'admin' | 'viewer';                     // union of string literals — most teams prefer this

Numeric enums are risky because their underlying values are just numbers — a value of 0 could silently be any enum member depending on declaration order, and enums compile to real runtime JS objects (unlike a union of string literals, which is erased entirely at compile time, adding zero runtime cost). Most modern teams prefer a plain union of string literals over enums for exactly these reasons — same compile-time safety, no runtime footprint, no ordering fragility.

Type inference (related)

TypeScript infers types from initializers automatically (let x = 5 is inferred as number) — the idiomatic style relies on inference for local variables and only annotates function signatures and exported values explicitly, since annotating every variable is noisy without adding real safety.

Basic What's the difference between readonly and const, and what does as const do?

const prevents reassigning a variable binding. readonly prevents reassigning a property after construction — but only at the type-checking level, and only shallowly (a readonly property holding an object doesn't make that object's own nested properties readonly, unless you make them readonly recursively too). 

interface Config { readonly apiUrl: string; }
const cfg: Config = { apiUrl: '/api' };
cfg.apiUrl = '/v2';  // compile error — readonly

let value = 'Hello' as const;         // const assertion → type is the literal 'Hello', deeply readonly
let length = (value as string).length; // type assertion → treat it as string instead

as const tells TypeScript to infer the most specific literal type for an expression instead of widening it to a general type — useful for object/array literals used as fixed configuration or enum-like values.

Basic What is a type assertion (as), and why is it dangerous?

A type assertion overrides TypeScript's inferred type with one you specify — used when you have more information than the compiler does (e.g. you know a DOM query returns a specific element type). It performs no runtime check — an incorrect assertion compiles cleanly and only fails later, at runtime, often far from where the actual mistake was made. 

let value: any = 'Hello';
let length = (value as string).length; // compiles fine even if value were actually a number

Common mistake: treating as SomeType as if it validates the data — it's purely a compiler instruction, not a runtime check. For data crossing a real boundary (an API response), validate with a runtime schema library instead, exactly as covered in the API-contract-drift scenario later in this guide.

3. Intermediate questions

Intermediate Explain generics with a real example from an API layer.
What

Generics let a function/type be parameterized over a type, preserving type information instead of widening to any. 

async function fetchJson<T>(url: string): Promise<T> {
  const res = await fetch(url);
  return res.json() as T;
}
interface Trade { id: string; notional: number; ccyPair: string; }
const trades = await fetchJson<Trade[]>('/api/trades'); // trades is Trade[], fully typed
Common mistake

Casting with as T and assuming that makes the data safe — it's a compile-time assertion only; the response could still be malformed at runtime. For real safety, validate with a schema library (Zod/io-ts) and infer the type from the schema.

Intermediate Discriminated unions — why are they the preferred pattern over optional fields? 
type RequestState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: string };

function render<T>(state: RequestState<T>) {
  switch (state.status) {
    case 'success': return state.data;   // TS knows `data` exists here
    case 'error':   return state.error;  // TS knows `error` exists here
  }
}

A single object with data?: T; error?: string; loading?: boolean allows invalid states (e.g. loading: true and data present at once) — the type system can't stop that. A discriminated union makes invalid states unrepresentable: the compiler narrows the type inside each case automatically, which is exactly the pattern behind React Query's/RTK Query's status objects.

Intermediate How does TypeScript narrow union types with typeof, in, and instanceof — and how is that different from a discriminated union? 
function format(value: string | number) {
  if (typeof value === 'string') return value.toUpperCase(); // narrowed to string
  return value.toFixed(2);                                    // narrowed to number
}

interface Bird { fly(): void; }
interface Fish { swim(): void; }
function move(animal: Bird | Fish) {
  if ('fly' in animal) animal.fly();   // narrowed to Bird
  else animal.swim();                  // narrowed to Fish
}

typeof narrows primitives, instanceof narrows class instances, and in narrows based on whether a property exists on the shape — all three work by checking something about the value at the call site. A discriminated union (covered above) is a different, more deliberate design choice: you add an explicit tag field up front specifically so narrowing is trivial and exhaustive everywhere the union is used, rather than relying on ad hoc structural checks each time.

Intermediate Most-used utility types — what do they do?

ReturnType<F> Extracts a function's return type
Awaited<T> Unwraps a Promise's resolved type
Intermediate Explain TypeScript's access modifiers (public/private/protected) — and how they differ from real runtime privacy.

public (the default) is accessible from anywhere. private is accessible only within the declaring class. protected is accessible within the class and its subclasses. These are compile-time only — they don't produce actual runtime privacy; the property still exists on the object and is reachable from plain JavaScript or by bypassing the type checker ((instance as any).privateField). For real runtime privacy, use native #field private class fields instead, which JavaScript itself enforces.

Intermediate interface vs class — what's the actual difference?

An interface is a compile-time-only contract describing a shape — it generates zero JavaScript output; it's erased entirely by the time the code runs. A class is a runtime construct — it compiles to an actual constructor function/prototype and can be instantiated with new. A class can implement one or more interfaces, and TypeScript checks that it actually satisfies each one's shape.

Intermediate What does the keyof operator do? 
interface Person { name: string; age: number; }
type PersonKey = keyof Person; // "name" | "age"

function getProp<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

keyof produces a union of a type's property names as string-literal types. It's most useful combined with generics and indexed access (T[K]) to write type-safe "get/set a property by name" utilities that stay correct even as the underlying type changes — this is exactly the mechanism behind the type-safe pick function in the coding challenges section below.

4. Advanced questions

Advanced Write a custom type guard and explain why it's needed over a plain boolean check. 
interface Cat { kind: 'cat'; meow(): void; }
interface Dog { kind: 'dog'; bark(): void; }

function isCat(pet: Cat | Dog): pet is Cat {
  return pet.kind === 'cat';
}

function speak(pet: Cat | Dog) {
  if (isCat(pet)) pet.meow(); // narrowed to Cat inside this block
  else pet.bark();            // narrowed to Dog
}

The pet is Cat return type ("type predicate") is what tells the compiler to actually narrow the type in the calling scope — a function that just returns boolean checks the same condition at runtime but gives the compiler no narrowing information, so you'd still need a cast afterward.

Advanced Mapped types and conditional types — build a DeepPartial<T>. 
type DeepPartial<T> = T extends object
  ? { [K in keyof T]?: DeepPartial<T[K]> }
  : T;

The conditional (T extends object ? ... : T) stops recursion at primitives; the mapped type ([K in keyof T]) iterates every key and recursively applies the same rule to nested objects — useful for typing a "patch" function against a deeply nested settings/config object.

Advanced How do you type React function components, hooks, and event handlers correctly (not just React.FC)? 
interface ButtonProps {
  label: string;
  onClick: (event: React.MouseEvent<HTMLButtonElement>) => void;
  variant?: 'primary' | 'secondary';
}
function Button({ label, onClick, variant = 'primary' }: ButtonProps) {
  return <button className={variant} onClick={onClick}>{label}</button>;
}

function useToggle(initial = false): [boolean, () => void] {
  const [value, setValue] = useState(initial);
  const toggle = useCallback(() => setValue(v => !v), []);
  return [value, toggle];
}

Prefer typing props with a plain function signature (function Button(props: ButtonProps)) over React.FC<ButtonProps> — React.FC implicitly adds children (not always wanted) and complicates generic components; most modern codebases and the React team's own guidance have moved away from it. When a component genuinely does accept children, type it explicitly instead of relying on React.FC's implicit version: interface CardProps { title: string; } combined with function Card({ title, children }: React.PropsWithChildren<CardProps>) — this documents that children are expected without pulling in everything else React.FC bundles.

Advanced Abstract classes vs interfaces — when do you reach for one over the other?

An interface can never contain implementation — only shape. An abstract class can provide real, partial implementations that subclasses inherit, alongside abstract members that subclasses are forced to implement, and it can't be instantiated directly on its own. Reach for an abstract class specifically when subclasses should share concrete, reusable behavior (not just a contract) — e.g. a base Widget class with a working render() orchestration method but an abstract getContent() each subclass must define. If there's no shared implementation to inherit, an interface is the simpler, more flexible choice (a class can implement several interfaces, but only extend one class).

Advanced What is variance (covariance/contravariance) in TypeScript, and why does it matter for function parameters specifically?

Covariance means a more specific type can be used where a more general one is expected — this is how TypeScript treats function return types: a function returning Dog is assignable where a function returning Animal is expected, because a caller getting a Dog back is still perfectly happy receiving "an Animal." Contravariance is the reverse, and it's how parameter types should ideally behave for real type safety: a function that can handle any Animal parameter should be assignable where a function handling only Dog is expected — accepting a wider range of input is safe, accepting a narrower range is not. 

type AnimalHandler = (a: Animal) => void;
type DogHandler = (d: Dog) => void;

let handler: AnimalHandler;
const dogHandler: DogHandler = (d) => console.log(d.bark());
handler = dogHandler; // unsound if allowed unchecked — handler may be called with a Cat,
                       // but dogHandler assumes it always gets a Dog

TypeScript's function parameters are bivariant by default for historical compatibility with older JS callback patterns (method parameters specifically), which is technically unsound — the snippet above compiles without error even though it isn't fully safe. Enabling strictFunctionTypes in tsconfig.json makes standalone function type parameters properly contravariant (catching cases like this), though method shorthand syntax remains bivariant even then, which is a real, frequently-cited gotcha at this depth.

Advanced How would you simulate nominal typing in TypeScript using branded types?
The problem

Because TypeScript is structurally typed, two differently-named types with the same shape are interchangeable — UserId and OrderId both typed as plain string can be passed to each other's functions with no compile error, even though mixing them is a real bug.

The fix
type UserId = string & { readonly __brand: 'UserId' };
type OrderId = string & { readonly __brand: 'OrderId' };

function getUser(id: UserId) { /* ... */ }

const orderId = 'ord_123' as OrderId;
getUser(orderId); // compile error — OrderId is not assignable to UserId

Intersecting the base type with a unique, unused "brand" property makes each branded type structurally distinct from the others, even though they're all just strings at runtime — the brand only exists at the type level and costs nothing in the compiled output. This is the standard workaround for simulating nominal typing in an otherwise structural type system.

Advanced Decorators, namespaces, and ambient declarations — do you need these in a React codebase?

Rarely written directly in plain React code, but worth recognizing: decorators (@Component, @Injectable) attach metadata/behavior to classes or members at declaration time — common in Angular and NestJS, uncommon in React. Namespaces (namespace Foo { ... }) are an older TS-only way to group code under a shared name; ES modules (import/export) are the modern standard, and recommending namespaces for new code is an outdated-practice flag in review. Ambient declarations (.d.ts files) describe the shape of code that isn't itself written in TypeScript — an untyped npm package, or a global injected by a <script> tag — so the compiler can type-check usages of it without needing the original source.

5. Expert-level & scenario-based

Expert Scenario: your team keeps typing API responses by hand and they drift from the real backend contract, causing runtime errors TypeScript didn't catch. How do you fix the process, not just the code?

TypeScript types are erased at compile time — they give zero runtime protection against a backend contract change. Fixes, in order of investment: (1) generate types directly from the API contract (OpenAPI/Swagger codegen, or GraphQL codegen) so the type is the contract, not a hand-maintained guess; (2) for critical payloads, validate at the network boundary with a runtime schema library (Zod) and infer the static type from the schema (z.infer<typeof schema>) so compile-time and runtime checks can never drift apart; (3) add contract tests against a staging backend in CI.

Expert Output-based: why does this fail to compile, and what's the fix? 
function merge<T, U>(a: T, b: U): T & U {
  return { ...a, ...b };
}
interface Base { id: string; }
interface Extra { id: number; } // conflicting `id` type
const x = merge<Base, Extra>({ id: '1' }, { id: 2 });
// x.id has type `string & number` — the intersection of incompatible
// primitive types collapses to `never`, so x.id is unusable

Intersections of object types combine all properties, but when the same key has incompatible primitive types across both, the resulting property type is never — a signal the two shapes shouldn't have been merged in the first place. The fix is to redesign the types so overlapping keys are compatible, or use a discriminated union instead of an intersection.

6. Coding challenges

Problem: implement a type-safe pick function 
function pick<T, K extends keyof T>(obj: T, keys: K[]): Pick<T, K> {
  const result = {} as Pick<T, K>;
  keys.forEach(key => { result[key] = obj[key]; });
  return result;
}

Follow-up: "Why K extends keyof T instead of just string[]?" — it constrains the caller to only pass keys that actually exist on T, and lets the return type be computed precisely via the built-in Pick utility rather than widened to Partial<T>.

Problem: type a reducer with a discriminated action union 
type Action =
  | { type: 'increment'; payload: number }
  | { type: 'reset' };

function reducer(state: number, action: Action): number {
  switch (action.type) {
    case 'increment': return state + action.payload; // payload known here
    case 'reset': return 0;
    default: {
      const _exhaustive: never = action; // compiler error if a case is missing
      return state;
    }
  }
}

Common mistake: skipping the never exhaustiveness check in the default branch — without it, adding a new action type later won't produce a compile error anywhere, silently breaking the reducer.

Problem: type a generic useLocalStorage<T> hook 
function useLocalStorage<T>(
  key: string,
  initialValue: T
): [T, (value: T) => void] {
  const [value, setValue] = useState<T>(() => {
    try {
      const item = window.localStorage.getItem(key);
      return item ? (JSON.parse(item) as T) : initialValue;
    } catch {
      return initialValue;
    }
  });

  const setStoredValue = (newValue: T) => {
    setValue(newValue);
    window.localStorage.setItem(key, JSON.stringify(newValue));
  };

  return [value, setStoredValue];
}

The generic T flows from the caller's initialValue into both the state type and the setter's parameter type, giving full type safety without callers ever specifying T explicitly — it's inferred. Common mistakes: not lazy-initializing state (the non-lazy form would read localStorage on every single render); not wrapping JSON.parse in a try/catch (corrupted storage crashes the app on mount). Follow-up: "How would you sync this value across browser tabs?" — listen for the window's storage event, which fires in other tabs (not the originating one) whenever localStorage changes.

7. Common mistakes & debugging

Frequent review comments Reaching for any under deadline pressure instead of unknown + narrowing; using non-null assertions (value!) to silence errors instead of fixing the actual null-handling; enabling TypeScript but leaving strict: false, which quietly disables most of the safety it's meant to provide; typing Redux/Context state with broad any-ish shapes instead of discriminated unions, losing exhaustiveness checking.

8. Frequently asked at top product companies

  • Microsoft/Google style: "Write a generic DeepReadonly<T>" or "explain variance (covariance/contravariance) in function parameters."
  • Meta style: Typing a real component's props precisely, including polymorphic as props (render a Button as an <a> or <button>).
  • Amazon/Adobe style: "Design types for a paginated API response" — tests generics + utility types together.
