Frontend System Design Interview Guide

A repeatable framework for the open-ended "design a ___" round, plus five worked examples chosen around your actual background — data grids, real-time dashboards, and enterprise-scale UI.

1. What this round actually tests

Unlike coding rounds, there's rarely a single "correct" answer here. Interviewers are evaluating whether you can: gather the right requirements before designing anything, break a fuzzy problem into components with clear responsibilities, reason about data flow and state ownership, and explicitly discuss trade-offs (there is always a trade-off — the interviewer wants to hear you name it, not pretend your design has none). At the 12-year/lead level, you're also expected to talk about team and scale concerns: how multiple engineers work on this without stepping on each other, how it's tested, and how it degrades gracefully under failure.

2. A framework you can reuse every time (RADIO)

StepWhat you doTime budget (45 min round)
RequirementsClarify functional requirements (what must it do) and non-functional ones (scale, latency, offline support, accessibility, devices)~5 min
ArchitectureHigh-level component tree / module boundaries, sketch the page as boxes~10 min
Data modelShape of client-side state, what's server-owned vs client-owned, normalization~10 min
Interface (API)Contracts between components/modules and with the backend — props, events, endpoints~10 min
OptimizationsPerformance, accessibility, error handling, edge cases, monitoring~10 min
Don't skip step R The single most common failure mode is diving into architecture before asking "how many rows/users/concurrent updates are we talking about, and does this need to work offline or on mobile?" Two candidates who both design "a data grid" but one clarifies "50 rows, refreshed hourly" vs "50,000 rows, updating every second" should produce visibly different designs — if yours doesn't change, that's the interviewer's biggest red flag.

3. Worked example: Design a high-performance data grid (your AG Grid domain)

Worked example "Design a data grid that can display and edit 100,000 rows of trade data."
Requirements (clarify first)

Read-only or editable? Sortable/filterable per column? Does data update in real time (price ticks) or is it a static snapshot? Row grouping/pinning needed? Must it be accessible (screen-reader-navigable rows)? Desktop-only or must it work on tablet?

Architecture

Virtualized viewport (render only visible rows + overscan buffer, absolutely positioned via transform: translateY(), with a spacer element to preserve real scrollbar height) — see the React guide's virtualization section for the mechanics. Column-virtualization too if there are many columns. A header component decoupled from body scroll but horizontally synced. A dedicated "cell renderer" registry so different columns (currency, date, status badge, editable input) can plug in custom render/edit components without the grid core knowing about domain types.

Data model

Normalized store: rowIds: string[] + rowsById: { [id]: Row }, so a single-row update (one price tick) only touches one map key, not the whole array reference — critical so unrelated rows don't re-render. Sort/filter state kept separate from raw data — compute a derived, memoized visibleRowIds array rather than mutating/reordering the source data.

Interface

Column definitions as a declarative config (field, header, width, renderer, editable flag, comparator) — this is exactly AG Grid's colDefs pattern — so consuming teams configure columns without touching grid internals. Edit events bubble up as onCellValueChanged(rowId, field, newValue) so the host app owns the actual persistence/validation logic.

Optimizations & trade-offs

Debounce/batch high-frequency updates (WebSocket ticks) to animation-frame boundaries instead of dispatching a render per tick. Accessibility trade-off: virtualization removes off-screen rows from the DOM, which breaks native browser find-in-page and can confuse screen readers about total row count — mitigate with ARIA aria-rowcount/aria-rowindex and a live region announcing sort/filter changes. Trade-off to state explicitly: building this in-house vs adopting a mature library (AG Grid) — for most teams, adopting is the right call; only justify building custom for extreme scale or a licensing constraint.

4. Worked example: Design a real-time trading/reconciliation dashboard

Worked example "Design a dashboard showing live FX/rates positions updating via a market-data feed, with per-user permissions."
Requirements

Update frequency (per-second? sub-second?), does every user see identical data or a permission-filtered subset, is historical/audit data needed, what happens if the WebSocket connection drops mid-session?

Architecture

A single WebSocket connection manager (not one per widget) that fans out updates to subscribed components via a pub/sub layer — multiple widgets on the same page (blotter, summary tiles, chart) shouldn't each open their own socket. Reconnect-with-backoff logic and a visible "stale data" indicator when the connection is down, rather than silently showing frozen numbers.

Data model

Normalized entity store per instrument/position (same reasoning as the grid example). Permissions applied at the selector layer, not by filtering the raw feed client-side for security — the backend must only ever send data the user's session is authorized for; a client-side filter is UX, not access control.

Interface

Widgets subscribe to specific entity IDs or topics rather than the whole feed, so a summary tile watching 5 instruments isn't re-rendered by updates to the other 9,995.

Optimizations

Throttle UI updates to the browser's paint cadence even if the feed delivers faster; consider whether every tick needs to touch global state at all, versus updating a ref/local subscription for the highest-frequency values and only syncing to the shared store at a reduced interval for cross-widget consistency and audit logging.

5. Worked example: Design a typeahead/autocomplete component

Worked example "Design a search autocomplete with remote suggestions."

Requirements: latency budget for suggestions, keyboard navigation (arrow keys, Enter, Escape), does it need to work offline/cache recent queries. Architecture: debounced input → request layer with in-flight request cancellation (a newer keystroke should cancel/ignore the previous request's response — the same race condition covered in the JS guide) → a small local cache keyed by query string to avoid re-fetching repeated prefixes. Interface: the component accepts a pluggable fetchSuggestions(query) function so it's reusable across different data sources (symbols, addresses, usernames). Optimizations: ARIA combobox/listbox roles for accessibility, minimum-character threshold before firing a request, and a clear empty/error state instead of a silently frozen dropdown.

6. Worked example: Design a notification system

Worked example "Design an in-app notification system (toasts + a notification center)."

Requirements: transient toasts vs persistent notification history, real-time push vs polling, read/unread state, multiple notifications queued at once. Architecture: a single notification queue/store (not one per triggering component) with a render layer (toast stack) subscribing to it — this avoids race conditions where two parts of the app both try to show a toast and one gets lost. Data model: notifications as normalized entities with id, type, read, createdAt, payload; unread count as a derived/memoized selector, not a separately-tracked counter that can drift out of sync. Optimizations: ARIA live regions so screen readers announce new toasts without stealing focus; a max-visible-toast limit with a queue for the rest, so a burst of events doesn't flood the screen.

7. Worked example: Design a resumable file upload with progress

Worked example "Design a file upload component supporting large files, progress, and resume after failure."

Requirements: max file size, single vs multi-file, must uploads survive a page refresh/network drop? Architecture: chunked upload (split large files into fixed-size chunks, upload sequentially or with limited parallelism, track per-chunk completion) so a failure only requires retrying the failed chunk, not the whole file. Data model: upload state machine per file — queued → uploading → paused → completed → failed — with chunk-level progress tracked separately from file-level status. Optimizations: exponential backoff retry per chunk, a persisted upload-session ID (server-side) so refreshing the page can resume rather than restart, and clear, per-file error messaging instead of one generic "upload failed" banner.

8. Architecture & team-scale questions

Architecture "How would you structure a component library / design system that multiple product teams consume?"

Publish it as a versioned, independently-installable package (npm workspace or private registry) rather than copy-pasting components across repos. Enforce a strict public API per component (props contract) with Storybook as the living documentation and visual-regression testing (Chromatic or similar) to catch unintended visual changes before release. Use semantic versioning and a deprecation policy so consuming teams can upgrade on their own schedule instead of being broken by an unannounced change — this is the single biggest source of friction in shared component libraries at scale.

Architecture "When would you reach for micro-frontends, and what do you give up by doing so?"

Micro-frontends make sense when genuinely independent teams need to ship on independent timelines with independent tech-stack choices (e.g. a legacy Angular module alongside a new React module during a phased migration), or when different sections of a large app have very different scaling/ownership needs. The cost: duplicated framework runtime bytes shipped to the browser unless carefully shared, harder cross-module state sharing, more complex build/deploy tooling (Module Federation or similar), and inconsistent UX if design-system governance isn't strict. For most single-team or single-org products, a well-organized monolith with clear feature-folder boundaries is simpler and should be the default; micro-frontends are a scaling solution to an organizational problem, not a performance optimization.

9. Common mistakes candidates make in this round

What actually gets candidates dinged Jumping straight to component/box diagrams without clarifying scale or requirements first; designing as if there's only one "correct" answer instead of naming trade-offs out loud; ignoring accessibility and error/empty/loading states entirely; forgetting that client-side checks (permissions, validation) are UX only — real enforcement must live server-side; spending the whole round on architecture and leaving no time to discuss performance, testing, or monitoring.

10. Frequently asked at top product companies

  • Amazon/Google style: "Design an infinite-scroll product feed" or "design a real-time collaborative document editor" — tests virtualization + conflict resolution/state ownership.
  • Meta/Airbnb style: "Design a news feed" or "design a booking calendar" — tests data modeling and optimistic UI updates.
  • Fintech-specific (directly relevant to your background): "Design a live order/position blotter" or "design a reconciliation dashboard reflecting two data sources (internal ledger vs external confirmation) with mismatches highlighted."
