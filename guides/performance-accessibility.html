Web Performance & Accessibility Interview Guide

Core Web Vitals, the optimization techniques that actually move them, and WCAG accessibility — treated together because in a real audit they're solved with overlapping techniques (semantic HTML, lazy loading, careful DOM management).

1. Overview

Performance and accessibility are two of the "quality" axes senior candidates are expected to own without being told to — nobody writes a ticket saying "please make this accessible," it has to be built in. Interviewers test whether these are habits, not afterthoughts: do you reach for semantic HTML by default, do you know what Core Web Vitals actually measure and why, and can you diagnose a real performance or accessibility bug rather than just recite definitions.

2. Core Web Vitals — the metrics that matter

MetricMeasuresGood thresholdMain causes when poor
LCP (Largest Contentful Paint)Time until the largest visible element renders< 2.5sSlow server response, render-blocking CSS/JS, unoptimized hero images, late-loading fonts
INP (Interaction to Next Paint — replaced FID in 2024)Responsiveness of the page to user interactions, across the whole session< 200msLong JS tasks blocking the main thread during/after an interaction, excessive re-renders
CLS (Cumulative Layout Shift)Visual stability — how much content unexpectedly shifts< 0.1Images/ads/embeds without reserved dimensions, late-injected banners, web fonts causing text reflow (FOUT/FOIT)

3. Basic questions

Basic Why did Google replace FID with INP as a Core Web Vital?

FID (First Input Delay) only measured the delay before the first interaction started processing — it said nothing about how long that processing took, or about any interaction after the first one. INP measures the full responsiveness of every interaction throughout the page's lifetime (input delay + processing time + time to next paint), reporting a representative worst-case — a much more honest picture of whether a page stays responsive as a session goes on, not just at first touch.

Basic What causes Cumulative Layout Shift, and what's the single most common fix?

CLS happens when visible elements move after the user has already started perceiving the page — most often images/iframes without explicit dimensions (the browser doesn't know how much space to reserve until the resource loads, so content jumps once it arrives), or content injected above existing content (a banner, a cookie notice) without reserved space. The single most common fix: always set explicit width/height (or an aspect-ratio box) on images and embeds so the browser reserves the correct space before the resource loads.

Basic What are the four WCAG principles (POUR)?

Perceivable (content must be presentable in ways users can perceive — alt text for images, captions for video, sufficient color contrast), Operable (all functionality available via keyboard, no content that traps focus or requires precise timing users can't control), Understandable (readable, predictable, with clear input error messages), Robust (works with a wide range of assistive technologies, valid/semantic markup they can parse reliably).

4. Intermediate questions

Intermediate Walk through the concrete techniques you'd apply to reduce a slow LCP.

1) Preload the LCP resource itself (<link rel="preload" as="image"> for a hero image, or preloading critical fonts) so the browser fetches it earlier instead of discovering it late in the HTML/CSS parse. 2) Eliminate render-blocking resources — defer non-critical CSS/JS, inline critical above-the-fold CSS. 3) Optimize the image itself — correct format (WebP/AVIF), correct size for the viewport (responsive srcset), and a CDN. 4) Reduce server response time (TTFB) — caching, edge rendering, faster backend queries. 5) Avoid client-side-only rendering for the LCP element if possible — if it depends on a client-side fetch-then-render waterfall, consider SSR/SSG for that content instead.

Intermediate How do you reduce a large JS bundle size in a React app?

Route-based code splitting (React.lazy + Suspense, or Next.js's automatic per-route splitting) so users only download the code for the page they're on. Analyze the bundle (webpack-bundle-analyzer or similar) to find unexpectedly large dependencies — a common surprise is an entire date/utility library imported for one function; switch to a tree-shakeable import (import { format } from 'date-fns' instead of the whole library) or a lighter alternative. Dynamically import() heavy, rarely-used features (a chart library only needed on one admin page) instead of bundling them into the main chunk. Audit and remove unused dependencies and dead code paths.

Intermediate When is a <div onClick> not accessible, and how do you fix it properly? 
{/* Bad: not focusable, not announced as interactive, no keyboard support */}
<div onClick={handleSave}>Save</div>

{/* Good: use the semantic element built for this */}
<button onClick={handleSave}>Save</button>

{/* If you truly must use a non-semantic element (rare), add the missing pieces yourself */}
<div
  role="button"
  tabIndex={0}
  onClick={handleSave}
  onKeyDown={e => (e.key === 'Enter' || e.key === ' ') && handleSave()}
>
  Save
</div>

A native <button> is focusable by default, announced as "button" by screen readers, and already responds to both Enter and Space — reaching for the semantic HTML element is almost always simpler and more correct than re-implementing all of that with ARIA and manual key handlers, which is why the accessibility community's mantra is "no ARIA is better than bad ARIA."

Intermediate How do you identify unnecessary re-renders in a React app before deciding what to optimize?

Start with the React DevTools Profiler — record an interaction, and its flame graph shows exactly which components re-rendered and (with "why did this render" enabled) what prop or state change triggered each one. This turns "I think this re-renders too much" into a concrete, measured claim instead of a guess — the same profile-first discipline the React guide's memoization questions rely on. For a recurring, systemic problem (a component that shouldn't re-render but keeps doing so across many interactions), a library like why-did-you-render can patch React to log every avoidable re-render automatically during development, which is more practical than manually profiling every single interaction by hand.

Intermediate Code-splitting has trade-offs too — when can splitting too aggressively actually hurt performance?

Every additional chunk is a separate network request — over-splitting (a separate chunk per tiny component instead of splitting at meaningful route or feature boundaries) can mean the browser fires off dozens of small requests instead of a few well-sized ones, and each request carries its own overhead (even with HTTP/2 multiplexing reducing connection overhead, there's still per-request processing cost). The practical guidance: split at route boundaries by default (from the React Router and Next.js guides), and add component-level splitting only for genuinely heavy, conditionally-rendered widgets (a large charting library, a rich text editor) — not reflexively for every component, which trades one performance problem (a large initial bundle) for another (request waterfall overhead and more cache-invalidation surface area).

Intermediate How do you make a custom dropdown/combobox accessible, and what's the difference between aria-label, aria-labelledby, and aria-describedby?
Accessible combobox pattern

A custom dropdown needs the ARIA combobox pattern layered on top of correct keyboard handling: the input gets role="combobox" with aria-expanded reflecting whether the option list is open, and aria-activedescendant pointing at the id of the currently-highlighted option (rather than moving actual DOM focus into the list, which would leave the text input unable to keep receiving keystrokes). The option list itself gets role="listbox", each option role="option", and arrow keys move the "active" highlighted option while Enter selects it and Escape closes the list — all of this on top of the semantic-HTML-first instinct from the question above; ARIA here is filling a real gap native elements can't express, not replacing something semantic HTML already handles.

The three ARIA labeling attributes
AttributeUse when
aria-labelNo visible text label exists at all — provides one directly as a string (an icon-only close button)
aria-labelledbyVisible text already exists elsewhere on the page that should serve as the label — references that element's id
aria-describedbyAdditional supplementary description beyond the label — e.g. pointing at a validation error or hint text associated with a field

Common mistake: using aria-label to override a visible label with different text than what's displayed — this creates a mismatch between what a sighted user reads and what a screen reader announces, which is disorienting for anyone using both (a low-vision user with partial screen-reader assistance, for example).

5. Advanced questions

Advanced A data grid virtualizes rows so only visible ones exist in the DOM (from the System Design guide). How do you keep that accessible for screen-reader users, who now perceive far fewer rows than logically exist?

Set role="grid" on the container with aria-rowcount reflecting the total logical row count, and aria-rowindex on each rendered row reflecting its true position — so assistive technology can announce "row 4,521 of 100,000" even though only ~30 rows are physically in the DOM at once. Provide a way to jump/search rather than relying purely on scrolling (a "go to row" or filter input), since screen-reader users can't efficiently scroll through a virtualized list the way sighted mouse-users do. This is a genuine trade-off to name explicitly in a system design interview: virtualization for performance vs the extra ARIA bookkeeping it requires for equivalent accessibility.

Advanced Explain how you'd audit and fix focus management in a single-page app with modals and route transitions.

Modals: on open, move focus into the modal (typically the first focusable element or the modal's heading), trap Tab/Shift+Tab cycling within it (focus trap) so keyboard users can't tab out to the obscured background content, and on close, return focus to the element that originally triggered the modal — not to document.body, which disorients keyboard/screen-reader users. Route transitions: in a client-rendered SPA, the browser doesn't automatically move focus or announce the new page the way a full page load does — move focus to the new page's main heading (or a designated "skip to content" landmark) on navigation, and consider an ARIA live region announcing the new page title, so screen-reader users get the same "new page" signal sighted users get from the visual change.

Advanced How would you reduce Time to Interactive on a large SSR page with heavy hydration cost?

The core problem: a fully server-rendered page shows content immediately (good LCP), but stays non-interactive until React has hydrated the entire tree — on a large, component-heavy page, that hydration work can itself become a long main-thread task that delays INP even though the page visually looks ready. Three complementary fixes, all variations on "don't hydrate everything eagerly": (1) selective/partial hydration — hydrate above-the-fold, immediately-interactive pieces first and defer the rest; React's Suspense-based streaming SSR supports this natively today. (2) Islands architecture (the pattern behind frameworks like Astro) — most of the page ships as static, non-hydrated HTML, and only specific "islands" of genuine interactivity (a cart widget, a comment form) ship their own JS and hydrate independently, rather than treating the whole page as one React tree that must hydrate together. (3) Below-the-fold code splitting — wrap non-critical, below-the-fold interactive sections in React.lazy so their JS doesn't even download until the user scrolls near them. All three share the same underlying idea from the System Design guide: not every pixel on the page needs the same priority, and hydration cost should scale with actual interactivity needs, not total page size.

6. Expert-level & scenario-based

Expert Scenario: "Lighthouse score dropped after a recent release — walk through your triage process."

Work from most-likely to least-likely, using the release itself as the primary lead rather than starting a generic performance audit from scratch: (1) diff the bundle size between the previous and current release — a bundle analyzer comparison (from the Webpack & Babel guide) usually surfaces an unexpectedly large new dependency immediately. (2) Check for newly added synchronous, heavy computation on the main thread, or a new third-party script (analytics, a chat widget, an ad tag) that's blocking rendering — these often ship without the team realizing the perf cost. (3) Check for a new large above-the-fold image without explicit dimensions or a responsive srcset — a classic, easy-to-miss cause of both an LCP and a CLS regression in the same release. (4) If none of the above turns up the cause quickly, git bisect (from the Git guide) through the commits in the release against a repeatable Lighthouse run, narrowing down to the exact commit that introduced the regression. The key discipline being tested here: use the fact that something specific just changed as a shortcut, rather than re-auditing the whole page from zero every time a score regresses.

Expert Scenario: Lighthouse scores are good in the lab, but real-user monitoring (RUM) shows LCP is much worse for actual users. Why might these disagree, and how do you investigate?

Lab tools (Lighthouse) run a single synthetic test on a fixed network/CPU profile and a cold cache — they don't capture the diversity of real users: slower devices, throttled/variable networks, ad blockers or extensions injecting scripts, third-party tags (analytics, chat widgets) that vary in load timing, or geographic latency to your CDN's edge nodes. Investigate with field data broken down by device class, connection type, and geography (via the CrUX report or your own RUM tooling) to find which segment is actually dragging the aggregate down, rather than continuing to optimize against a lab score that may already look fine. A common finding: a third-party script (chat widget, ad tag) that wasn't present in the lab test is blocking the main thread for real users.

Expert Scenario: an automated accessibility scanner (axe/Lighthouse) reports zero violations, but a real screen-reader user still can't complete the checkout flow. Why, and what's missing from automated testing?

Automated tools catch structural/markup-level issues (missing alt text, insufficient contrast, missing labels, invalid ARIA) — roughly 30-40% of WCAG success criteria are reliably automatable. They cannot evaluate whether the actual experience makes sense: whether the reading order matches the visual order, whether an error message is announced at the right moment relative to form submission, whether a multi-step flow's focus management genuinely lets a keyboard/screen-reader user progress without getting stuck. This is exactly why manual testing — actually navigating the flow with a screen reader (VoiceOver/NVDA/JAWS) and keyboard-only, ideally involving people who use assistive technology daily — remains necessary; automated scanning is a floor, not a substitute for it.

7. Common mistakes & debugging

Frequent review comments Images/iframes without explicit dimensions, causing layout shift; relying on color alone to convey meaning (a red input border with no text/icon for colorblind users); interactive <div>s instead of semantic elements; removing focus outlines (outline: none) without providing a visible alternative focus style; treating a green Lighthouse score as proof of "done" instead of a starting signal; optimizing bundle size once at launch and never re-auditing as dependencies accumulate over time.

8. Frequently asked at top product companies

  • General senior-level: "Walk me through how you'd improve this page's LCP/CLS" — often given an actual URL or Lighthouse report to react to live.
  • Accessibility-focused companies (and any regulated industry, including banking): "How do you make a custom dropdown/autocomplete component accessible?" — tests ARIA combobox pattern knowledge plus keyboard interaction design.
  • Performance-focused companies: "Bundle size grew 40% over six months with no single big change — how do you find out why, and how do you prevent it going forward?" (bundle analyzer + CI budget/threshold checks that fail a build if size regresses past a set limit).
