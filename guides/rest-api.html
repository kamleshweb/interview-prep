REST API Interview Guide

HTTP semantics, resource-oriented design, pagination, versioning, and the integration patterns you've actually used wiring React front-ends to bank-grade REST backends.

1. Technology overview

REST (Representational State Transfer) is an architectural style for HTTP APIs built around resources (nouns, not actions), standard HTTP methods carrying the verb, and statelessness — each request carries everything the server needs, with no server-side session state tied to it. For a senior frontend engineer, the bar isn't designing REST APIs from scratch (that's often a backend concern) — it's demonstrating you understand HTTP well enough to consume APIs correctly, design a sane contract when you're the one specifying it, and reason about caching, retries, and error handling on the client side.

2. Basic questions

Basic What makes an API "RESTful" — what are the actual constraints?

Client-server separation, statelessness (no session stored server-side between requests — auth must be re-sent, e.g. a token, on every call), a uniform interface (resources identified by URIs, manipulated through standard representations like JSON, using standard HTTP methods), cacheability (responses explicitly marked cacheable or not), and a layered system (client can't tell if it's talking directly to the origin server or through intermediaries like a gateway/CDN). Most "REST APIs" in the wild only loosely follow these (e.g. skip HATEOAS entirely) — which is fine and expected; interviewers care that you know the difference between practical REST and the formal constraints.

Basic GET vs POST vs PUT vs PATCH vs DELETE — what's the actual semantic difference, not just CRUD mapping?
Method Semantics Idempotent? Safe (no side effects)?
GET Retrieve a representation Yes Yes
POST Create a resource / non-idempotent action No No
PUT Replace a resource entirely Yes No
PATCH Partially update a resource Not guaranteed (depends on the patch semantics) No
DELETE Remove a resource Yes No

Idempotent means calling it once or ten times with the same input produces the same end state — PUT /trades/5 {status: 'confirmed'} called twice leaves the trade in the same confirmed state either way, whereas POST /trades called twice creates two trades.

Basic What do the main HTTP status code ranges mean, and name a few you should actually know precisely?

2xx success, 3xx redirection, 4xx client error, 5xx server error. Precisely: 200 OK, 201 Created (with a Location header pointing to the new resource), 204 No Content (success, empty body — common for DELETE), 400 Bad Request (malformed input), 401 Unauthorized (not authenticated — misleadingly named, it really means "unauthenticated"), 403 Forbidden (authenticated but not allowed), 404 Not Found, 409 Conflict (e.g. a version mismatch on update), 422 Unprocessable Entity (well-formed but semantically invalid), 429 Too Many Requests (rate limited), 500 Internal Server Error, 503 Service Unavailable.

Common mistake: returning 200 with an error message in the body — this breaks HTTP-level tooling (caches, monitoring, generic error-handling middleware) that relies on status codes to know something went wrong.

3. Intermediate questions

Intermediate Offset pagination vs cursor-based pagination — trade-offs?
Offset (?page=3&limit=20) Cursor (?after=abc123&limit=20)
Simplicity Simple, supports "jump to page N" No arbitrary page jumps, only next/prev
Consistency under writes Can skip or duplicate items if rows are inserted/deleted between page loads Stable — cursor is tied to a specific record, unaffected by inserts elsewhere
Performance at scale Large offsets get slower (DB still scans/skips prior rows) Consistently fast regardless of position

For a live-updating trade list where new rows are constantly inserted, cursor pagination avoids the classic "same row appears twice across two pages" bug that offset pagination is prone to.

Intermediate How do you version a REST API, and what are the trade-offs of each approach?
Approach Example Trade-off
URI versioning /v2/trades Most explicit/discoverable; clutters the URI; "resource" identity technically changes across versions
Header versioning Accept: application/vnd.bank.v2+json Keeps URIs clean; less discoverable, harder to test with just a browser/curl by hand
Query param /trades?version=2 Easy to add, easy to overlook/misuse as optional

Most production APIs (including large fintech ones) default to URI versioning for its simplicity and cache-friendliness, reserving header-based versioning for APIs needing finer content-negotiation control.

Intermediate How should client code handle a flaky network — retries, and why aren't all requests safe to retry blindly?

Only retry idempotent requests (GET, PUT, DELETE) automatically — retrying a POST blindly can create duplicate resources (e.g. double-submitting a trade). For non-idempotent operations that must be safely retryable, the API should support an idempotency key (a client-generated unique ID sent in a header) that the server uses to detect and de-duplicate retried requests, returning the original result instead of creating a second resource. On the client, use exponential backoff with jitter for retries, and only retry on transient failures (network errors, 5xx, 429 with a Retry-After header) — never blindly retry a 4xx.

4. Advanced questions

Advanced Design a consistent error response contract for an API — what should it include? 
{
  "error": {
    "code": "TRADE_VALIDATION_FAILED",
    "message": "Notional amount must be greater than zero",
    "field": "notional",
    "requestId": "req_8f2a1c",
    "details": [ { "field": "notional", "issue": "must be positive" } ]
  }
}

A machine-readable code (for programmatic handling, distinct from the human-readable message which may change wording), a requestId for correlating with server-side logs during support/debugging, and field-level detail for validation errors so a form can highlight the specific offending inputs instead of showing one generic banner. Consistency across every endpoint matters more than any specific shape — client error-handling code shouldn't need special cases per endpoint.

Advanced How does HTTP caching actually work for a REST API (ETag, Cache-Control, conditional requests)?

The server returns an ETag (a hash/version identifier of the resource) alongside a Cache-Control directive. On the next request, the client sends If-None-Match: <etag>; if the resource hasn't changed, the server responds 304 Not Modified with an empty body instead of re-sending the full payload — saving bandwidth while still letting the client confirm freshness rather than blindly trusting a TTL. This is also how optimistic-concurrency updates often work: sending If-Match: <etag> on a PUT/PATCH lets the server reject the update with 409 Conflict if the resource changed since the client last read it, preventing a lost-update race.

5. Expert-level & scenario-based

Expert Scenario: two users on a trade-editing screen both load the same trade, edit different fields, and save — the second save silently overwrites the first user's change. How do you fix this at the API level?

Classic lost-update problem. Fix with optimistic concurrency control: the GET response includes a version/ETag; the PUT/PATCH request must include that version (If-Match header or a version field in the body); if the server's current version doesn't match, it rejects with 409 Conflict instead of silently overwriting, and the client can then re-fetch, show a merge/conflict UI, or ask the user to redo their change against the latest state. This is strictly better than a pessimistic locking approach (locking the record while one user edits) for a UI-driven workflow, since it doesn't leave a resource locked if a user simply navigates away mid-edit.

Expert REST vs GraphQL vs gRPC — how do you actually decide for a new internal API?
REST GraphQL gRPC
Best for Public/simple CRUD APIs, wide tooling/caching support Complex UIs needing flexible, client-driven data shapes (avoid over/under-fetching) High-performance internal service-to-service calls
Caching Native HTTP caching (ETag, CDN-friendly) Harder — typically POST-based, needs custom caching N/A — not typically browser-facing
Learning curve Low, ubiquitous Medium — schema, resolvers Higher — protobuf, HTTP/2, less browser-native

For a browser-facing dashboard with several distinct views each needing a different slice of trade data, GraphQL genuinely solves a real over-fetching problem. For a public or partner-facing API, REST's simplicity, caching, and tooling ubiquity usually win. The honest interview answer is scenario-dependent — naming the actual trade-off beats declaring a universal favorite.

6. Common mistakes & debugging

Frequent review comments Using verbs in URIs (/getTrades) instead of resource nouns (GET /trades); returning 200 for errors; not distinguishing 401 from 403; blindly retrying non-idempotent POST requests on network failure, risking duplicate creation; ignoring Retry-After on 429 responses and hammering a rate-limited endpoint; putting sensitive data in query strings (logged in server/proxy access logs) instead of the body or headers.

7. Frequently asked at top product companies

  • Amazon/general style: "Design the REST API for a URL shortener / a bookmarking service" — tests resource modeling, status codes, and idempotency reasoning together.
  • Fintech-specific (relevant to your background): "How would you prevent double-submission of a trade if a user double-clicks 'Confirm' or the network retries the request?" — tests idempotency keys directly.
  • General senior-level: "Walk through what happens end-to-end when a PUT request updates a resource two clients are both viewing" — tests optimistic concurrency / ETag reasoning.

8. Cheat sheet / quick revision

Concept One-line recall
Statelessness No server-side session between requests — auth resent every time
Idempotent Same result no matter how many times you call it — GET/PUT/DELETE, not POST
201 vs 200 vs 204 Created / OK with body / success no body
401 vs 403 Not authenticated vs authenticated-but-forbidden
Cursor pagination Stable under concurrent writes; offset pagination isn't
ETag / If-Match Conditional requests — enables caching AND optimistic concurrency
Idempotency key Client-generated ID that makes a POST safely retryable
