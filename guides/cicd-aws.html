CI/CD & AWS Interview Guide

Pipeline design, deployment strategies that reduce risk, and the AWS building blocks (EC2, S3, CloudFront) most frontend deployments actually touch.

1. Overview

CI (Continuous Integration) is about catching problems early — every change is automatically built and tested before it merges. CD (Continuous Delivery/Deployment) is about getting validated changes to users safely and repeatedly, ideally with minimal manual intervention. Given your resume shows hands-on CI/CD pipeline and basic AWS (EC2, S3) exposure across multiple roles, expect practical, workflow-level questions rather than deep infrastructure-engineering ones — the senior-frontend bar here is "can you reason about how your code gets from a merged PR to a live URL, and what could go wrong along the way."

2. Basic questions

Basic What's the difference between Continuous Delivery and Continuous Deployment?

Both mean every change that passes the pipeline is production-ready. Continuous Delivery stops short of actually deploying automatically — a human clicks "deploy" (often for business/release-timing reasons). Continuous Deployment goes all the way — every change that passes all automated gates deploys to production with no manual approval step at all. The distinction is entirely about that last manual gate, not about pipeline quality.

Basic What are the typical stages of a frontend CI/CD pipeline, in order?

Install dependencies (with lockfile-verified, cached installs) → lint/type-check → unit/integration tests → build (bundle for production) → optionally, bundle-size/performance budget checks → deploy to a staging environment → E2E tests against staging → (manual approval, if Continuous Delivery) → deploy to production → smoke tests/health checks against production. Each stage should fail fast — if linting fails, there's no reason to spend time running a full test suite or building.

Basic At a basic level, what do S3 and CloudFront do for hosting a frontend app, and why are they used together?

S3 (Simple Storage Service) is object storage — for a static frontend build, it holds the actual HTML/CSS/JS/asset files. On its own, S3 serving directly to users would mean every request travels to wherever that S3 bucket's region is, and doesn't benefit from edge caching. CloudFront is AWS's CDN — it caches S3's content at edge locations around the world, so users get the app served from a nearby edge node instead of the origin bucket, and it also handles HTTPS termination and can enforce cache-control behavior centrally. The typical pattern: build artifacts uploaded to S3, CloudFront distribution in front of that bucket as the actual public-facing endpoint.

3. Intermediate questions

Intermediate Blue-green vs canary deployment — what's the difference, and when would you pick one over the other?
Blue-Green Canary
Mechanism Two full environments (blue = current, green = new); switch all traffic at once once green is verified Roll the new version out to a small % of traffic first, gradually increase if healthy
Rollback speed Instant — just switch the router back to blue Fast — stop the rollout and route remaining traffic back to the old version
Risk exposure All-or-nothing — a bad deploy affects 100% of users the instant it's switched Limited — a bad deploy only affects the small canary cohort before it's caught
Cost/complexity Requires maintaining two full environments Requires traffic-splitting infrastructure and good real-time monitoring to catch issues in the canary cohort quickly

For a high-stakes app (financial dashboard) where a bad deploy is expensive, canary's gradual exposure is usually preferred despite the added infra complexity — it catches problems while only a small fraction of users are affected, rather than everyone at once.

Intermediate How do you handle environment-specific configuration (dev/staging/prod API URLs, feature flags) safely in a CI/CD pipeline?

Never hardcode environment values into the source or bake secrets into the client bundle (anything shipped to the browser is publicly visible, so no API keys/secrets belong there at all). Use environment variables injected at build time (per-pipeline-stage config, e.g. a different .env.production vs .env.staging consumed during the build step) for anything safe to be public (API base URLs, public feature-flag service keys), and keep genuine secrets (private API keys, database credentials for any server-side pieces) in a dedicated secrets manager (AWS Secrets Manager, or the CI provider's encrypted secrets store), injected only into the specific pipeline steps that need them, never into the client-facing build artifact.

Intermediate Why does a CI pipeline run tests again in a clean environment if they already passed on the developer's machine?

"Works on my machine" often means the developer's machine has some implicit state a fresh environment doesn't — a globally installed dependency version, a cached build artifact, an environment variable set once and forgotten, or a different OS/Node version. Running the full pipeline in a clean, reproducible container/VM for every single change is what actually verifies the change is correct in isolation, not just correct given whatever accumulated state happens to be on one developer's laptop — this is precisely the guarantee CI is meant to provide.

4. Advanced questions

Advanced How would you design a rollback strategy for a frontend deployed via S3 + CloudFront, given that a bad deploy is discovered 20 minutes after release?

Keep every deployed build as its own versioned/timestamped folder in S3 (never overwrite "latest" in place) — rollback then becomes simply repointing CloudFront's origin path (or updating an index/manifest object it reads) back to the previous known-good build's folder, which propagates in minutes without needing to rebuild anything. Combine this with a CloudFront cache invalidation for the entry HTML file specifically (so the rollback is visible immediately, not delayed by cached TTLs), while long-lived, content-hashed asset files (JS/CSS with a hash in the filename) don't need invalidation at all since a rollback simply references the old hashed filenames again. The key architectural decision that makes fast rollback possible at all is immutable, versioned deploys — never deploying by overwriting the previous build in place.

Advanced What's the difference between EC2 and a serverless/managed hosting approach for a frontend app, and when might you actually still need EC2?

A static frontend build (HTML/CSS/JS with no server-side rendering) has no real need for EC2 at all — S3 + CloudFront serves it more cheaply and with less operational overhead (no servers to patch, scale, or monitor). EC2 (or a container service) becomes relevant when you need actual server-side compute at request time — an SSR Next.js app that renders per-request, a lightweight API/BFF (backend-for-frontend) layer aggregating calls to internal services, or a WebSocket server for real-time features. The senior-level framing: default to static hosting for anything that can be static, and only reach for compute infrastructure (EC2, containers, Lambda) for the specific pieces that genuinely need server-side execution.

5. Expert-level & scenario-based

Expert Scenario: a deploy passed every automated test in the pipeline but broke a critical flow in production within minutes. What pipeline gaps would you investigate, and what would you add?

First question: did staging actually mirror production closely enough (same environment config, same data shape/scale, same third-party integrations) — a very common gap is staging using mocked/seeded data that doesn't exercise the real edge case that broke in prod. Second: were the E2E tests covering the actual critical flow that broke, or just a happy-path subset — critical-path E2E coverage should be treated as non-negotiable even if the rest of the suite is thinner. Additions to consider: canary/gradual rollout instead of an all-at-once deploy (so this class of failure only hits a small cohort before being caught by automated health-check monitoring), automated rollback triggers tied to real-time error-rate/latency monitoring rather than relying on someone noticing manually, and a post-incident process that turns this specific gap into a new automated test so the same class of failure can't reach production silently again.

6. Common mistakes & debugging

Frequent review comments Overwriting the same S3 "latest" build in place instead of versioned/immutable deploys, making rollback slow or impossible; baking secrets into the client-side bundle; skipping E2E tests against a true staging environment and only running them against mocks; deploying 100% of traffic at once for a high-risk change instead of a canary/gradual rollout; no automated rollback trigger, relying entirely on someone noticing a spike in errors manually.

7. Frequently asked at top product companies

  • General senior-level: "Walk me through what happens from merging a PR to it being live for users" — tests full pipeline understanding end to end.
  • Reliability-focused companies: "How would you design a deployment strategy that minimizes blast radius for a bad release?" — tests canary/blue-green reasoning.
  • Fintech-style (relevant to your background): "How do you handle secrets and environment-specific config for a regulated application across dev/staging/prod?"
