Security & Auth Interview Guide

XSS, CSRF, CSP, and token-storage trade-offs — the frontend-facing slice of application security, especially relevant given your background on a regulated financial platform.

1. Overview

Frontend security interviews focus on a specific, well-known set of client-side attack vectors and the concrete defenses against each. For a candidate with banking-domain experience (CFTC/EMIR compliance context on your resume), expect this round to carry real weight — security-conscious teams in regulated industries screen for this explicitly, not just as a box-ticking topic.

2. Basic questions

Basic What is XSS (Cross-Site Scripting), and how does React protect against it by default?

XSS is injecting attacker-controlled script into a page that then executes in a victim's browser session — typically by getting untrusted user input rendered as live HTML/JS instead of inert text. React escapes any value interpolated into JSX by default ({userInput} is always rendered as text, never parsed as HTML), which closes off the most common injection path automatically. The escape hatch, dangerouslySetInnerHTML, is named the way it is deliberately — using it with any untrusted/user-provided content re-opens exactly this vulnerability, which is why any use of it should go through a sanitization library (like DOMPurify) first.

Basic What is CSRF (Cross-Site Request Forgery), and how is it different from XSS?

XSS runs malicious code inside your site's own origin. CSRF doesn't need to run any code on your site at all — it tricks a victim's browser into making a request to your site (e.g. by submitting a hidden form on a malicious page) while the victim is still authenticated there, so the browser automatically attaches their session cookie, and the server can't tell the request wasn't intentional. Defenses: CSRF tokens (a per-session, unpredictable token the server requires on state-changing requests, which an attacker's page has no way to know), and SameSite cookie attributes that prevent the cookie from being sent on cross-site requests in the first place.

3. Intermediate questions

Intermediate Where should an auth token be stored: localStorage, sessionStorage, or an httpOnly cookie — and why?
localStorage/sessionStorage httpOnly cookie
XSS exposure Fully readable by any JS on the page — a single XSS hole leaks every token Not accessible to JS at all (that's what httpOnly means) — immune to being read by an XSS payload
CSRF exposure Not automatically attached to requests — CSRF doesn't apply the same way Automatically attached by the browser to matching-origin requests — needs CSRF defenses
Convenience Simple, manual header attachment Automatic, but requires server cooperation (Set-Cookie, SameSite config)

The security-conscious default, especially for a financial application: httpOnly, Secure, SameSite cookies for the token itself, paired with CSRF-token defenses on state-changing requests — trading a CSRF surface (well-understood and defensible) for eliminating the XSS-token-theft surface entirely (a much more severe, harder-to-fully-close class of risk). This is a genuine trade-off worth naming explicitly rather than a one-sided "cookies are always better" claim.

Intermediate What is Content Security Policy (CSP), and what's a concrete example of what it prevents? 
Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted-cdn.com

CSP is a response header that tells the browser exactly which sources are allowed to load scripts, styles, images, etc. from — anything not on the allowlist is blocked, even if an XSS vulnerability somehow got malicious script into the page's HTML. A strict script-src that excludes 'unsafe-inline' means even a successful HTML-injection attack still can't execute an inline <script> tag — CSP acts as a second layer of defense that assumes the first layer (input sanitization) might fail, which is exactly the "defense in depth" principle security reviewers look for. When a React app genuinely needs to load a specific third-party script (an analytics tag, a payment widget), the fix is adding that exact origin to the relevant directive (script-src 'self' https://js.stripe.com) rather than loosening the policy broadly with 'unsafe-inline' or a wildcard — a narrowly-scoped allowlist entry preserves almost all of CSP's protection, while a wildcard defeats the point of having one at all.

Intermediate What is clickjacking, and how do you prevent it?

Clickjacking loads your page inside an invisible or disguised <iframe> on an attacker's site, tricking a user into clicking something (a "claim your prize" button, say) that's actually positioned over a real, sensitive control on your page underneath (a "transfer funds" or "delete account" button) — the user sees the attacker's fake UI but their click lands on yours. Prevent it with the X-Frame-Options header (DENY or SAMEORIGIN) or the more flexible modern replacement, the CSP frame-ancestors directive (frame-ancestors 'self'), which tells the browser to refuse to render your page inside a frame on any other origin at all. For a banking-style application, this is typically a non-negotiable default header on every response, not something opted into per page.

Intermediate What is CORS, and why does it exist as a browser mechanism rather than a server-side-only concern?

CORS (Cross-Origin Resource Sharing) is a browser-enforced check: by default, JS running on one origin can't read the response of a request made to a different origin (the Same-Origin Policy). CORS headers (Access-Control-Allow-Origin and related) are how a server explicitly opts specific origins into being allowed to read its responses. It's enforced by the browser, not the server — the request itself often still reaches the server either way, but the browser withholds the response from the calling JS if CORS doesn't permit it. This is a common point of confusion: CORS is a client-side protection against malicious sites reading data from an API on a victim's behalf, not a server-side access-control mechanism on its own — real authorization still has to happen server-side regardless of CORS configuration.

4. Advanced questions

Advanced How do you handle third-party dependency vulnerabilities in a large frontend codebase, practically?

Automated scanning (npm audit, Snyk, Dependabot, or similar) integrated into CI so a vulnerable dependency fails the build or at minimum flags a PR, rather than being discovered manually or after the fact. Beyond detection: a policy for how quickly different severity levels must be addressed (critical vulnerabilities patched immediately vs lower-severity ones batched into regular maintenance), and — importantly — actually reading the advisory to understand whether the vulnerable code path is even reachable in your usage before treating every finding as equally urgent (a vulnerability in a dev-only build tool is a very different risk than one in a runtime dependency shipped to the browser).

Advanced How would you secure a client-side form that handles sensitive financial data (e.g. entering trade details) beyond basic HTTPS?

HTTPS is the baseline, not the whole answer. Beyond that: strict CSP to limit what can execute even if an injection succeeds; input validation and sanitization on both client (UX) and server (actual enforcement — client-side checks are always bypassable); avoiding autocomplete/browser-storage of sensitive field values where inappropriate (autocomplete="off" on genuinely sensitive fields); ensuring no sensitive data ends up in browser history via GET query strings (covered in the REST APIs guide) or in client-side logs/error-tracking payloads that might inadvertently capture form state; and session timeout/re-authentication for high-value actions, so a briefly unattended, still-logged-in session isn't a standing risk on a shared or unlocked device.

5. Expert-level & scenario-based

Expert Scenario: a security review flags that your app is vulnerable to XSS via a "rich text" comment/notes field that renders user-submitted HTML (bold, links, etc.). How do you fix it while still supporting rich formatting?

The fix isn't to ban rich text — it's to never trust the raw HTML directly. Sanitize the user-submitted HTML server-side (and again client-side as defense-in-depth) through a well-maintained sanitization library (DOMPurify is the standard client-side choice) configured with an explicit allowlist of safe tags/attributes (<b>, <i>, <a href> with a scheme check to block javascript: URLs) rather than a denylist trying to catch every dangerous pattern — allowlists are far more robust against novel attack payloads than trying to enumerate everything to block. Only after sanitization does the content go anywhere near dangerouslySetInnerHTML. A stricter alternative some teams prefer entirely: don't accept raw HTML from users at all — accept a constrained markup format (Markdown, or a custom rich-text JSON structure) and render it through your own trusted renderer, eliminating the raw-HTML attack surface altogether.

6. Common mistakes & debugging

Frequent review comments Using dangerouslySetInnerHTML with unsanitized user content; storing auth tokens in localStorage for convenience without weighing the XSS trade-off; assuming CORS is an access-control mechanism rather than a browser-side protection, and skipping real server-side authorization; no CSP at all, removing a valuable defense-in-depth layer; trusting client-side validation as sufficient without server-side enforcement; not rotating/expiring sessions for high-sensitivity actions.

7. Frequently asked at top product companies

  • General senior-level: "Where would you store a JWT, and why?" — tests the localStorage-vs-httpOnly-cookie trade-off directly.
  • Security-conscious/regulated companies (highly relevant to your background): "Walk through how you'd secure a form handling sensitive financial data end to end."
  • General senior-level: "Explain the difference between XSS and CSRF, and the defense for each" — near-universal frontend security question.
